# Jev 与类型化决策模型

本课是“模型选型与前沿案例”选修，知识归属连接第二层技术地图、第四层路由评测和第五层产品选型。前置：[分类、概率与评测基础](/learn/classification-probability-basics)、[评测与可观测性](/learn/agent-evaluation-observability)。先能计算误报与漏报、区分概率与校准，再比较 Jev。学完交一张规则 / 分类器 / LLM / Jev 对照实验设计表；没有服务访问或真实数据时明确标为待验证，不填写虚构实测成绩。

> 资料核对：2026-09-21。TypeSafe 于 2026-09-15 宣布 Jev 并开放 early access。System One Model 是 TypeSafe 提出的类别名称，本课不把它当成学界统一分类。发布事实见 [官方公告](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。本项目尚未接入 Jev，以下示例是教学设计，不是运行测评。

## 一 · 它解决什么问题

传统聊天模型常把结果写成文字；有些软件只需要在固定选项中做一次判断。TypeSafe 将 Jev 定位为接收状态与类型化问题、返回供代码消费的结构化决策的模型，当前不以自由文本生成为目标。官方还提出 RLCD（Reinforcement Learning for Calibrated Decisions）作为其训练方法名称；不能仅凭发布说明推断未披露的内部层数、参数量或完整训练配方。[官方公告](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

例如客户连续两次创建活动失败，每次等待超过 20 分钟，已经投诉。业务需要的是“走哪个处理队列”，未必需要模型先写一篇解释。先定义紧急程度的互斥边界，再让模型判断；是否告警、转人工以及谁有权限执行，仍由软件规则决定。

## 二 · 在地图里放在哪里

```text
AI：研究与构建智能行为的总领域
  方法轴：规则、机器学习、深度学习、强化学习……
  任务轴：生成、分类、检索、评分、决策……
  模型/产品实例：LLM、分类模型、Jev……
  应用架构：RAG、Workflow、Agent……
  集成协议：MCP、A2A……
```

“生成型模型 / 决策型模型”在这里是按主要任务和输出接口做的比较，**不是互斥且穷尽的 AI 技术树**。LLM 也能分类、打分、选择工具，可以使用结构化输出；传统分类器早就在做概率预测。Jev 提供的是面向这类任务的一种新产品和训练/接口设计，不是“AI 首次能做判断”。

放回世界观：接收状态 → 内部表征与预测 → 类型化判断 → 业务策略 → 工具执行。Jev 可以参与 Agent 的某个判断节点，但它本身不等于拥有规划、记忆、权限和执行循环的完整 Agent。

## 三 · 三种问题接口

TypeSafe 当前文档区分三种原语。一个调用可包含多个问题，各问题基于同一状态独立评估；若后一个问题必须依赖前一个答案，应由程序显式组织依赖。[官方概览](https://docs.typesafe.ai/introduction)

| 原语 | 问什么 | 读结果时注意 |
| --- | --- | --- |
| Choice | 从预定义选项选一项，如投诉类别 | 返回选择、各选项概率和 confidence；类别不应漏掉未知/其他情况 |
| Score | 按有序标准打分，如问题影响程度 | 返回评分、各等级概率和 confidence；评分不是事件发生概率 |
| Noul | 一个命题是否成立，如是否明确要求人工 | 返回 0–1 的 noul；没有单独的 confidence 字段 |

Choice 的字段与选项规则见 [Choice 文档](https://docs.typesafe.ai/primitives/choice)；Score 是有序等级位置的概率加权结果，见 [Score 文档](https://docs.typesafe.ai/primitives/score)；二值判断见 [Noul 文档](https://docs.typesafe.ai/primitives/noul)。具体限制、版本与 API 以使用时官方文档为准。

## 四 · 投诉分流：从概率到行动

先定义业务标准。例如 low 为未阻断且无时限的咨询，medium 为可绕过的功能问题，high 为单客户业务阻断，critical 为经证据确认的大面积中断或明确关键截止期风险。再增加“资料不足”的处理路径。标准需要业务人员验证；“用户很生气”不能自动等于“全站严重事故”。

下面只是抽象结果，**不是 Jev 的实测输出或完整 API 响应**，也不表示给定投诉一定应判 critical：

```json
{
  "low": 0.01,
  "medium": 0.02,
  "high": 0.14,
  "critical": 0.83
}
```

代码使用的是“概率 + 业务代价 + 权限 + 资料充分性”。概念伪代码如下；0.8 仅用于教学，不是通用上线阈值。

```text
如果请求无权限：停止写入
否则如果关键字段缺失或模型调用失败：转人工分流
否则如果 critical 的概率 > 0.8：标记优先复核
否则：按已验证规则进入普通处理队列

如需修改工单或通知他人：由授权工具执行，并记录结果
如需向客户解释：由 LLM 起草，依据可核对的事实复核
```

真实系统可能更关心漏掉严重投诉的损失。即使 critical 没达到最高概率，high 与 critical 的合计风险、客户时限或已确认的服务故障也可能要求复核。这是**业务策略设计**，不能让模型分数自动取代。

## 五 · 三个最容易误读的“可靠”

**类型正确，不等于判断正确。** 输出只能在合法标签内，也可能把严重事故误分为普通咨询。发布文章中的“无幻觉”相关表述主要借助 schema / 类型约束讨论，不能据此承诺事实正确、抵抗注入、无偏见或零业务错误。其类型图表的 0% 不是本项目的实测正确率。[官方公告及其限制说明](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

**confidence 不等于选项概率。** TypeSafe 的 Choice / Score confidence 是从完整概率分布计算的集中程度统计量。不能把 `confidence = 0.83` 直接读成“这条判断有 83% 的正确率”，也不能假设它等于最大的选项概率。[官方 confidence 文档](https://docs.typesafe.ai/confidence)

**校准是样本集合上的性质。** 在有足够代表性的独立标注集上，把预测某类概率接近 0.8 的样本放在一起，查看该类实际出现频率是否也接近 0.8；这不保证某一条预测正确。用可靠性图、Brier score 或 log loss 等检查，再按语言、业务类型和时间分组查看。分布变化后需要重新验证。概率校准的基础研究可参考 [On Calibration of Modern Neural Networks](https://proceedings.mlr.press/v70/guo17a.html)。

## 六 · 与哪些方案一起比较

| 候选 | 合理用法 | 仍要验证 |
| --- | --- | --- |
| 规则引擎 | 已确认故障、次数、时限与权限 | 规则覆盖、数据质量和维护成本 |
| 传统分类器 | 标签稳定且有标注数据 | 冷启动、校准与领域迁移 |
| LLM + 结构化输出 | 语义分类、抽取、解释与复杂任务 | schema 遵守和语义正确是不同指标 |
| Jev | 有限选择、评分与原子概率判断 | 业务误差、概率校准、接口可靠性 |
| LLM / Agent 与决策模型组合 | 先查证，再判断，再由工具执行 | 端到端质量、额外延迟和失败恢复 |

速度与费用需要同条件比较。TypeSafe 的公开 workflow eval 使用外部模型的预测作为参考，并说明自建工作流和运行条件可能带来偏差；这类结果不是客户标注的真值，更不能直接推出某项目的 ROI。可查看 [官方评测入口](https://evals.typesafe.ai/) 与 [公告中的评测限制](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。本课程不把宣传倍数写成通用性能保证。

## 七 · 在本项目怎样做一个最小实验

可以离线整理一批问题，标注“闲聊 / 典籍查证 / 排盘说明 / 资料不足”，先比较现有规则、一个 LLM 分类调用与 Jev 候选判断。把题目、模型版本、规则版本、样本来源、正确标签、预测分布、耗时与失败类型记成表。

第一轮只分析结果，不改变聊天路由；第二轮考虑影子运行；只有在路由正确率、严重误分、成本与尾延迟均达到约定标准后，才讨论接入。Jev 不应替换来源校验、权限判断、精确排盘算法，也不应凭判断分数编造缺失典籍。[评测课程](/learn/agent-evaluation-observability) 提供验证框架。

## 八 · 练习与参考答案

1. “Jev 类型安全，所以能直接批准任意操作。”哪里错？
2. 100 条预测 critical 概率约 0.8 的代表性样本中，只有 45 条标注为 critical，可以直接按 0.8 阈值上线吗？
3. 为什么一次给出标签的调用，不一定构成 Agent？

**参考答案**：类型约束只限制输出空间，授权与业务正确性需要独立验证。第二题显示这批样本中概率与频率有明显差异，应检查样本量、标签标准与分布，重新评估校准和阈值；还要测阈值对应的漏报与人工量。第三题缺少环境反馈与动态动作循环，它可能只是 Workflow 的一个分类节点。
