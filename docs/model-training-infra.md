# 模型训练与 AI 基础设施

> 位置：五层地图第 3 层的进阶篇，连接第 4 层工程实践。前置：[Transformer 与模型训练机制](/learn/transformer-mechanics)。

## 学习目标

- 区分改变上下文、微调模型、从头预训练。
- 理解 LoRA 的参数节省来自哪里，以及它仍有哪些成本。
- 用权重、缓存、激活和训练状态拆解内存预算。
- 根据质量、流量、延迟与运维要求比较 API 和自托管。
- 为训练或部署方案写出评测与回滚条件。

## 一 · 三种不同的改进路径

| 路径 | 改变什么 | 适合先验证的问题 |
|------|----------|------------------|
| Prompt、Context、RAG | 当前调用收到的指令与信息 | 资料缺失、示例不足、任务表达不清 |
| Fine-tuning（微调） | 已有模型的全部或部分可训练参数 | 在一类任务上形成更稳定的行为 |
| Pretraining（预训练） | 从初始化或继续训练中学习数据规律 | 需要建立或扩展基础模型能力 |

“从头预训练”是预训练的一种；已有模型也可以继续预训练。小模型的训练实验与前沿基础模型的训练资源差别很大，不能用一个固定金额描述所有预训练。

微调可能改善风格、格式或任务表现，但不保证事实都正确，也不保证每项通用能力都提升。预训练、后训练与推理的区别见 [模型原理](/learn/transformer-mechanics)。[Hugging Face：How do Transformers work?](https://huggingface.co/learn/llm-course/chapter1/4)

## 二 · 什么时候值得微调

从一个可衡量的问题开始：“使用相同测试集，角色表达一致率是否提高，同时引用正确率不下降？”不要从“我们也要有自己的模型”开始。

```
建立基线与保留测试集
  → 错误归因：知识、提示、格式、能力还是系统执行问题？
  → 尝试能解决该问题的低成本方案
  → 若有稳定任务、足够的高质量数据与可测目标，比较微调
  → 检查收益、退化、推理成本与维护成本
  → 达标才上线，保留旧版本以便回滚
```

天道茶寮的教学例子：若问题是“找不到某段典籍”，先改知识处理和检索；若问题是“引用已给对，但同类回答风格反复跑偏”，可以比较更好的示例、声口校验和微调。两类问题可以同时存在。

**微调不是不可逆，也不是永远的最后手段。** 保留原始权重、适配器和部署版本就能切回。是否值得做取决于评测收益与总成本；托管微调服务也不要求使用者自己购买 GPU。

## 三 · 全量微调、LoRA 与软提示

| 方法 | 可训练对象 | 主要取舍 |
|------|------------|----------|
| 全量微调 | 模型的全部目标参数 | 灵活，但训练状态与版本存储通常较大 |
| LoRA | 添加到选定权重上的低秩矩阵 | 可训练参数少，但仍需运行基础模型 |
| Soft Prompt / Prompt Tuning | 可学习的连续提示向量 | 区别于人工编写文字 Prompt；适配范围取决于任务与实现 |

LoRA 通常冻结原始权重 W，训练两个较小矩阵，并把它们的乘积作为权重更新：

```
有效权重 = W + 缩放系数 × B A

示例：W 为 10000 × 10000，共 1 亿参数
秩 r = 8
B 为 10000 × 8，A 为 8 × 10000
新增可训练参数 = 80000 + 80000 = 16 万
```

这说明单个矩阵的训练参数如何减少，不代表整套模型一定节省到相同比例。LoRA 的秩、目标模块和训练数据都要通过验证集选择；秩越大不保证效果越好。适配器可分别保存或在支持的实现中合并，回滚前要保留原始版本。[LoRA 原始论文](https://arxiv.org/abs/2106.09685)

即使只训练小适配器，前向计算、反向传播所需激活和基础权重仍有成本。“适配器文件只有几 MB”不能推导出“训练只需要几 MB 显存”。

## 四 · 训练数据与评测先于训练命令

一个可执行的训练计划至少需要：

1. 定义输入、理想输出与不允许退化的能力。
2. 检查数据来源、去重、清洗与标注一致性。
3. 划分训练集、验证集、保留测试集，避免近重复样本泄漏。
4. 记录基础模型、Tokenizer、数据版本、训练参数与代码版本。
5. 比较原模型、Prompt 基线与微调结果，检查代表性失败样本。
6. 规定上线门槛、监控指标和回滚版本。

SFT 中“模仿理想回答”与偏好训练中“比较多个回答”使用的数据结构和目标不同，不能只把聊天日志堆进去就当作完成训练数据设计。[InstructGPT 论文](https://arxiv.org/abs/2203.02155)

## 五 · GPU、CPU 与内存预算

GPU 擅长大规模并行张量计算；CPU 也能做模型推理，并承担数据处理、服务逻辑等工作。是否使用 GPU、用几张、是否卸载部分数据，要结合模型、框架、吞吐和延迟目标判断。

先算最简单的**权重存储**，再补齐运行成本：

```
权重字节数 ≈ 参数量 × 每参数字节数

假设模型恰好有 70 亿参数：
FP16 / BF16：70 亿 × 2 字节 ≈ 14 GB
8 bit：70 亿 × 1 字节 ≈ 7 GB
4 bit：70 亿 × 0.5 字节 ≈ 3.5 GB
```

以上是十进制 GB 的粗算，量化还可能有缩放因子等额外信息。**这不是所需显存的最终答案。**

| 场景 | 还要考虑什么 |
|------|--------------|
| 推理 | KV Cache、计算临时张量、框架开销、批量大小、并发与上下文长度 |
| 训练 | 梯度、优化器状态、激活、中间缓冲及可能的高精度权重副本 |
| 多设备 | 每台设备的分配、通信与并行策略 |
| 量化或卸载 | 精度影响、额外元数据、数据传输与速度 |

训练内存不是权重大小的一个永远固定的倍数；优化器、精度与激活检查点策略都会改变结果。先做配置估算，再用目标输入长度和并发实测峰值。[Hugging Face：GPU memory usage](https://huggingface.co/docs/transformers/en/model_memory_anatomy)

## 六 · 推理服务到底负责什么

```
请求
 → 鉴权、限流与排队
 → 模型与 Tokenizer 处理
 → Prefill 与 Decode
 → 流式或完整响应
 → 指标、错误与资源监控
```

服务可能使用批处理和不同缓存策略提升资源利用率。选择框架时应查看模型支持、硬件支持、协议、吞吐、延迟、运维成熟度，而不是只问“哪个最快”。Ollama、vLLM 等提供不同部署路径，真实表现需要在目标环境里比较。

要分清两件事：

- KV Cache：在生成过程中复用已经处理的 Token 的 K/V。[Hugging Face：缓存机制](https://huggingface.co/docs/transformers/en/cache_explanation)
- 前缀缓存：跨请求复用相同前缀的计算；命中通常减少输入处理工作，不会消除新答案的 Decode。[vLLM：前缀缓存](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)

本地服务提供“OpenAI 兼容”接口，通常意味着支持其中部分协议，并不保证每个模型、每种工具调用、流式事件或结构化输出特性完全一致。以 Ollama 为例，官方文档明确标注为支持 API 的一个子集；接入后仍要验证应用实际使用的能力。[Ollama：OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility)

## 七 · MLOps：管理的不只是模型文件

MLOps 将数据、训练、评测、部署和运行反馈连接成可追踪的流程：

```
数据版本 → 训练配置 → 模型版本 → 评测报告
   ↑                              ↓
失败样本与新需求 ← 监控与反馈 ← 部署版本
```

在 AI 应用里，还要把 Prompt、检索配置、工具定义与运行代码纳入版本管理。同一模型配上不同知识库与工具，也可能呈现完全不同的结果。

建议用一份发布记录串联：“哪个模型 + 哪套数据/知识 + 哪版代码 + 哪组评测”。仅记录模型名称，往往无法复现失败。训练集表现变好也不等于保留测试集或真实用户表现变好。

## 八 · 调 API 还是自托管

| 维度 | API 服务 | 自托管 |
|------|----------|--------|
| 资源 | 供应商管理模型运行资源 | 团队管理机器、容量和部署 |
| 成本 | 计费、网络、重试与集成维护 | 机器、能源、利用率、工程与运维 |
| 数据 | 核对服务条款、区域和数据流 | 能控制部署边界，但仍要检查日志与外部依赖 |
| 质量 | 按目标任务评测 | 同样按目标任务评测 |
| 延迟 | 网络、排队、模型与输出长度共同决定 | 本地网络可能更短，但硬件与排队仍决定体验 |
| 可用性 | 供应商能力与应用降级策略 | 团队自己的容量、冗余与运维能力 |

不要用“超过某个固定日调用量就该自建”作结论。输入长度、输出长度、流量峰值、模型大小与设备利用率都会改变账本。

一个课堂算账模板：

```
API 月成本 = 输入与输出计费 + 重试 + 配套服务 + 维护
自托管月成本 = 设备或租赁 + 能源 + 存储网络 + 运维人力

在相同成功率、峰值负载和延迟要求下比较：
每个成功完成任务的总成本
```

## 九 · 常见误区

- 微调可以回滚，前提是保留可恢复的模型与部署版本。
- LoRA 节省可训练参数，不会让基础模型的运行成本消失。
- 模型参数量与量化位数只能估算权重，不能代替显存实测。
- 本地运行也有硬件、能源和维护成本。
- 缓存提升计算复用，不保证模型知识更新或回答正确。
- 接口兼容不代表所有能力兼容；质量好坏也不能仅凭“开源/闭源”判断。

## 十 · 练习与参考答案

### 练习

1. 7B 参数、FP16 权重约 14 GB，为什么不能立即承诺 16 GB 显卡满足所有并发？
2. LoRA 训练后表现变差，如何恢复？
3. 课程知识每天变化，风格却很稳定。先做 RAG 还是训练？依据是什么？
4. 两个部署方案回答质量不同，只比较每百万 Token 价格有什么问题？

### 参考答案

1. 还需要 KV Cache、临时张量和服务开销；上下文、批量与并发影响峰值。14 GB 只是权重粗算。
2. 部署回原始模型或上一版适配器，恢复匹配的配置，再用失败样本和保留测试集定位退化。合并适配器前应保存原始权重。
3. 先验证检索更新流程。需求主要是及时提供外部知识，不是改变固定行为；仍需评测召回、证据与答案质量。
4. 便宜方案可能需要更多重试或人工返工。应在相同质量与延迟要求下，比较每个成功任务的总成本。
