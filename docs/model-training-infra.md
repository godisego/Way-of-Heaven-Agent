# 模型训练与 AI 基础设施

这篇是给"想从用模型到懂模型"的人写的。你不需要成为 ML 工程师，但理解模型训练的基础设施，能帮你做更好的技术决策。

> **前置**：读 [LLM 基础原理](/learn/llm-fundamentals) 再来这篇。这里讲的是"模型怎么来的"和"能不能自己训一个"。

## 一 · 从"用模型"到"训模型"

```
用别人的模型（RAG / Prompt Engineering）
  ├─ 不改模型参数
  ├─ 通过 prompt + 上下文改变行为
  ├─ 成本低、灵活
  └─ 天道茶寮走的这条路 ← 你在这里

微调别人的模型（Fine-tuning）
  ├─ 改模型部分参数
  ├─ 用自己的数据让模型学特定风格/知识
  ├─ 成本中等、需 GPU
  └─ 适合：特定风格、专业领域

从头训练模型（Pre-training）
  ├─ 从随机参数开始训
  ├─ 需要海量数据 + 大量 GPU
  ├─ 成本极高（百万~千万美元级）
  └─ 只有 OpenAI、Anthropic 等少数公司能做
```

**95% 的 AI 应用应该走第一条路**——用别人的模型 + RAG + Prompt。天道茶寮就是。

## 二 · Transformer 架构速览

不用看数学公式。用直觉理解 Transformer 的核心机制：

### 模型在干什么

```
输入："天行健君子以"
  │
  ├─ Tokenize → [天, 行, 健, 君, 子, 以]
  │
  ├─ Embedding → 每个 token 变成一个向量
  │
  ├─ 注意力机制（核心！）
  │   每个 token "看"其他 token，判断谁更重要
  │   "健" 看 "天行" → 理解"天行健"是一个整体
  │   "以" 看 "君子" → 理解"君子以"后面该接什么
  │
  ├─ 多层处理 → 从浅层语法到深层语义
  │
  └─ 输出概率 → "自"（概率 85%）、"强"（概率 90%）...
```

### 注意力（Attention）的直觉

```
没有注意力：
  "健" 只看自己 → 不知道是"天行健"还是"身体健"

有注意力：
  "健" 同时看所有 token，判断"天行"最相关
  → 理解这是"天行健"的"健"
```

**Transformer = 让每个词都能看到所有其他词，并判断谁更重要。** 这是 GPT/Claude/Llama 等所有现代 LLM 的基石。

## 三 · 微调（Fine-tuning）

### 微调解决什么问题

```
基础模型（GPT-4）：
  知识广但浅，什么都能聊但不够专业

微调后：
  在特定领域更准、风格更一致、格式更可控
```

### 微调的三种方式

| 方式 | 改什么 | 成本 | 适合 |
|------|--------|------|------|
| **全量微调** | 改所有参数 | 高 | 专业领域、数据多 |
| **LoRA** | 只改一小部分参数 | 中 | 特定风格、数据少 |
| **Prompt 微调** | 只调 prompt 向量 | 低 | 轻量定制 |

### 什么时候该微调

```
先问自己：RAG + Prompt 能解决吗？

├─ 能 → 不要微调（微调是不可逆的、有维护成本的）
├─ 不能但只是知识不够 → RAG（检索补充知识）
├─ 不能但只是格式不稳 → Prompt Engineering（加约束 + 示例）
└─ 不能且是风格/领域问题 → 考虑微调
```

### 天道茶寮该不该微调？

```
需求：让模型用"老胡的语气"说话

方案 A（当前）：Prompt + Few-shot + 声口校验
  优点：灵活、可随时调整、不花钱
  缺点：偶尔跑偏（重试兜底）

方案 B：微调一个"老胡模型"
  优点：风格更稳
  缺点：成本高、不可逆、维护难、改不了

→ 天道茶寮选方案 A（正确选择）
```

**关键判断**：如果你的问题能用 RAG + Prompt 解决，就不要微调。微调是"最后的手段"。

## 四 · LoRA 详解

LoRA = Low-Rank Adaptation = 不改原模型，只训练一个小"补丁"。

### 直觉理解

```
原始模型参数：
  [巨大矩阵 10000×10000 = 1 亿参数]
  ├─ 不动它
  │
  └─ 加一个"补丁"：
      [小矩阵 10000×8] × [小矩阵 8×10000]
      = 只训练 16 万参数（原来的 0.16%）
```

### LoRA 的优势

```
全量微调：
  原模型 10GB + 微调后模型 10GB = 20GB（存两份）

LoRA：
  原模型 10GB + LoRA 补丁 10MB = 10.01GB
  可以同时存多个补丁，按需切换
```

### 天道茶寮如果要微调

```python
# 用 Hugging Face PEFT 库做 LoRA 微调
from peft import LoraConfig, get_peft_model

# 1. 加载基础模型
model = AutoModelForCausalLM.from_pretrained("Qwen2.5-7B")

# 2. 配置 LoRA
lora_config = LoraConfig(
    r=8,                    # 秩（越大效果越好但越贵）
    lora_alpha=32,          # 缩放因子
    target_modules=["q_proj", "v_proj"],  # 对哪些层做 LoRA
    task_type="CAUSAL_LM",
)

# 3. 应用 LoRA
model = get_peft_model(model, lora_config)

# 4. 准备数据（三贤的对话样本）
train_data = [
    {"input": "我怎么面对中年危机", 
     "output": "【盲派算师·老胡】先看你的盘..."},
    ...
]

# 5. 训练
trainer.train()

# 6. 保存（只有补丁，很小）
model.save_pretrained("./lora-old-hu")  # ~10MB
```

## 五 · GPU 基础

训练和推理都需要算力。算力从 GPU 来。

### GPU vs CPU

```
CPU（4~16 核）：擅长复杂逻辑，一次做一件事
GPU（几千核）：擅长简单并行，同时做几千件事

训练模型 = 几千次矩阵乘法 = GPU 的主场
```

### 显存（最关键的指标）

```
模型大小 → 需要的显存

7B 参数模型（如 Qwen2.5-7B）
  ├─ 推理：~14GB（FP16）或 ~7GB（INT8）
  └─ 训练：~56GB（含梯度+优化器）

13B 参数模型
  ├─ 推理：~26GB
  └─ 训练：~104GB

GPT-4 级别（~1万亿参数）
  └─ 训练：需要几百张 A100，成本千万美元级
```

### 天道茶寮需要 GPU 吗

```
天道茶寮用 API 调别人的模型 → 不需要 GPU
如果要本地部署开源模型 → 需要 GPU（至少 7B × 14GB = 一张 16GB 显卡）
如果要微调 → 需要更大 GPU（7B LoRA 微调 ~24GB）
```

## 六 · MLOps 速览

MLOps = Machine Learning Operations = 模型从训练到上线的全流程管理。

### MLOps 全流程

```
数据准备 → 模型训练 → 模型评估 → 模型部署 → 监控 → 数据收集 → 回到第一步
                                                         │
                                                    持续循环
```

### 每个环节

| 环节 | 做什么 | 工具 |
|------|--------|------|
| 数据准备 | 收集、清洗、标注 | Python, Pandas |
| 模型训练 | 训练模型 | PyTorch, Hugging Face |
| 模型评估 | 测试准确率、泛化 | 自定义 eval set |
| 模型部署 | 上线推理服务 | vLLM, Ollama |
| 监控 | 延迟、错误率、漂移 | Prometheus, Grafana |
| 数据收集 | 用户反馈、失败 case | 日志系统 |

### 和 DevOps 的区别

```
DevOps（软件工程）：
  代码改了 → 测试 → 部署 → 监控
  改代码 = 改逻辑，确定性的

MLOps（机器学习）：
  数据改了 → 训练 → 评估 → 部署 → 监控
  改数据 ≠ 改逻辑，模型行为可能变好也可能变差
  → 需要更严格的版本管理和回归测试
```

## 七 · 推理服务

模型训练完了，怎么让别人能用？靠推理服务。

### 推理服务做什么

```
用户请求 → 推理服务 → 模型生成 → 返回结果
              │
         管理这些事：
         ├─ 模型加载到 GPU 内存
         ├─ 请求排队（多人同时问）
         ├─ 批处理（多个请求合并算，省 GPU）
         ├─ KV Cache（相同前缀不重复算）
         └─ 限流（防止滥用）
```

### 常见推理框架

| 框架 | 特点 | 适合 |
|------|------|------|
| **vLLM** | 高吞吐、PagedAttention | 生产环境高并发 |
| **Ollama** | 简单易用、本地跑 | 个人/开发 |
| **TGI**（HuggingFace） | 功能全 | 和 HF 生态绑定深 |
| **TensorRT-LLM** | NVIDIA 出品、最快 | 有 NVIDIA GPU 的生产 |

### 天道茶寮用推理服务吗

```
天道茶寮调外部 API（MiniMax/OpenAI）→ 不需要自己跑推理服务

如果改成本地部署开源模型：
  ├─ 用 Ollama 跑 Qwen2.5-7B
  ├─ 把 CHAT_BASE_URL 改成 http://localhost:11434/v1
  └─ 天道茶寮代码一行不用改（因为它用的是 OpenAI 兼容协议）
```

## 八 · 什么时候该自建 vs 调 API

| 维度 | 调 API（天道茶寮当前） | 自建（本地部署） |
|------|----------------------|------------------|
| **初始成本** | 0（注册就用） | 高（GPU + 部署） |
| **边际成本** | 按 token 付费 | 固定（电费+机器折旧） |
| **数据隐私** | 数据发给别人 | 数据不出本地 |
| **延迟** | 100~500ms（网络） | 10~100ms（本地） |
| **可用性** | 依赖供应商 | 自己保障 |
| **模型质量** | 顶级（GPT-4） | 中等（开源 7B~70B） |
| **维护** | 零维护 | 高（更新、监控） |

### 决策树

```
你的数据敏感吗？
├─ 是 → 本地部署（或用提供隐私保障的 API）
└─ 否 → 你的调用量大吗？
    ├─ 不大（<1万次/天）→ 调 API
    └─ 大（>10万次/天）→ 算账：API 费 vs 自建成本
```
