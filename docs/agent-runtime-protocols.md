# Agent 运行系统与协议

> **地图位置：第四层 · AI Engineering。** 前置：[Agent 工具循环](/learn/agent-loop)、[上下文工程与记忆](/learn/context-memory-engineering)。本课把“模型会选工具”推进到“系统能可靠完成任务”。

Agent 通常是围绕目标运行的软件系统。模型提出下一步，运行系统校验和执行，再把结果交回模型。模型、工具和运行系统要分别评价；换一个模型，不会自动补上持久化、权限和恢复能力。

## 一 · Runtime / Harness 在做什么

Runtime 常指执行与状态管理部分；harness 常指围绕模型的整套输入、工具、控制和验证机制。不同项目用词有重叠，理解职责比背术语重要。Anthropic 的长任务实践用进度记录和可验证的增量成果帮助后续会话接手；这是一个实现案例，不是所有 Agent 必须使用的框架。[官方长任务实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

```text
目标与当前状态
      ↓
装配上下文 → 模型提出动作
                   ↓
       校验参数 / 权限 / 预算 / 审批
                   ↓
                执行工具
                   ↓
       核验结果 / 更新状态 / 记录轨迹
                   ↓
      继续、等待输入、暂停或结束
```

这对应第一层的“获取环境信息 → 决策 → 行动 → 再感知”。模型生成一段 JSON 是动作提议；真正的数据库写入或页面点击由程序执行。

## 二 · 先确定控制权放在哪里

| 结构 | 下一步由谁决定 | 适合的任务 | 主要代价 |
|---|---|---|---|
| Workflow，工作流 | 代码预先规定主要路径 | 上传 → 解析 → 分块 → 入库 | 遇到例外需要新增明确分支 |
| Agent 循环 | 模型在约束内动态选动作 | 检索无命中后改写，再决定是否读原文 | 调用次数、延迟和路径不固定 |
| 混合结构 | 固定阶段中嵌入动态循环 | 受控取证后固定生成与校验 | 要说清每个阶段的完成条件 |
| 多 Agent | 多个独立执行上下文协作 | 能独立研究且结果可合并的子问题 | 协调、重复检索、共享状态冲突和成本 |

这里采用“预定义流程”和“模型动态决定流程”的区分；它不是严格的模型类别树。[Anthropic 对 workflow 与 agent 的定义](https://www.anthropic.com/engineering/building-effective-agents)

天道茶寮当前属于混合结构：取证阶段动态调用工具，随后进入生成和校验。三贤是输出角色与知识分工，不能仅凭三个人设就认定存在三个独立 Agent。

在引入多 Agent 前，先问：子问题能否独立完成？交付物和证据格式是否明确？谁有权修改共享状态？并行节省的时间是否抵得过协调和模型成本？如果答案不清楚，先把单个循环做稳。

## 三 · 能继续聊，不等于能恢复执行

会话摘要回答“之前谈了什么”。**Checkpoint，执行检查点** 回答“执行到了哪里，哪些结果已经提交，下一个可恢复步骤是什么”。LangGraph 的持久化机制是将图执行状态保存成检查点的一种实现参考；要看其实际持久化后端和恢复语义，不能只看到框架名字就假定能跨进程恢复。[官方持久化文档](https://docs.langchain.com/oss/javascript/langgraph/persistence)

以下是扩展系统的概念字段，不是本项目已有类型：

```json
{
  "runId": "run_example",
  "status": "waiting_approval",
  "nextStep": "publish_learning_plan",
  "artifactId": "draft_42",
  "artifactVersion": 3,
  "completedActions": ["retrieve_sources", "create_draft"],
  "approvalId": null,
  "deadline": "2026-09-21T12:00:00Z"
}
```

恢复时应重新读取这份状态，核对产物版本、当前权限和未完成动作。不能只把旧聊天记录重放一遍：旧记录可能说“开始发送”，而外部系统其实已经发送成功。

### 重试不等于重做

假设工具“发布学习计划”已经成功，但响应在网络中丢失：

1. 系统事先为这次业务动作生成稳定的 `idempotencyKey`，把动作意图写入持久存储。
2. 发出请求后保存外部结果编号；超时而结果未知时，先用业务编号或幂等键查询状态。
3. 只有接口承诺同键去重时，才使用同一个键安全重试；为重试生成新键会失去去重作用。
4. 如果外部系统既不能查状态也不支持去重，应进入“结果待核对”，交由人工或明确补偿流程处理。

这份流程是系统设计示例。**重复调用检测** 只防止模型卡在同一请求；**幂等执行** 处理重复投递后的业务副作用，二者不是同一个能力。超时也不证明任务没有发生，取消等待更不等于撤销已生效的动作。

### 人工审批要绑定具体动作

审批应包含对象、目标位置、内容版本和操作类型。例如“同意把草稿第 3 版发布到课程 A”。如果内容变为第 4 版，或目标换成公开网站，应重新判断授权是否仍覆盖。审批结果保存在结构化状态中，执行前由程序检查；“模型记得用户同意过”不够。

## 四 · Tool Calling、MCP、A2A、Skills 分别是什么

| 概念 | 所属抽屉 | 解决的问题 | 不自动提供什么 |
|---|---|---|---|
| Tool / Function Calling | 模型与应用之间的结构化调用机制 | 模型表达工具名称和参数，应用返回结果 | 实际执行、权限校验、业务幂等 |
| MCP | 应用与能力服务之间的互操作协议 | 发现和使用工具、资源与提示模板 | 长期记忆、正确答案、自动安全保证 |
| A2A | 不同 Agent 系统之间的互操作协议 | 发现能力、交换消息、追踪任务与产物 | 必须采用多 Agent、内部推理共享 |
| Agent Skills | 可复用的知识与工作步骤格式 | 按任务加载指令、脚本与参考资料 | 新模型权重、自动获得工具权限 |
| Plugin，插件 | 宿主产品定义的分发与集成包装 | 安装一组能力、配置或资源 | 跨所有产品统一的插件规范 |

MCP 的参与者是 Host、Client、Server：Host 管理应用体验和策略，内部 Client 与 Server 通信；Server 可提供 tools、resources、prompts。支持哪些特性，要以双方版本与能力为准。[MCP 架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

A2A 用 Agent Card 描述对外能力和接口，并定义消息、任务状态、产物等交互。它可以连接组织已有的专业 Agent 服务，并不要求把每个函数改成一个 Agent；同一产品内部的多 Agent 也不必采用 A2A。[A2A 官方规范](https://a2a-protocol.org/latest/specification/)

Agent Skills 的核心是含 `SKILL.md` 的目录，可附脚本和参考资源。宿主可以先读名称与描述，匹配任务后再加载详细内容。加载技能说明并不等于执行其中的所有动作，仍须遵守用户授权和宿主权限。A2A Agent Card 中的 skill 能力描述，也不要与 `SKILL.md` 目录格式直接等同。[Agent Skills 官方说明](https://agentskills.io/home)

一个系统可能同时使用它们：技能讲“怎么做核对报告”，模型用 Tool Calling 提议查库，应用通过 MCP 调用查库服务，再通过 A2A 把一个完整的资料核对任务委托给外部 Agent。这只是组合示例；三个工具的茶寮当前可以直接调用本地函数，无须为了名词齐全引入协议。

### 协议核对与版本边界

资料核对日期为 **2026-09-21**。MCP 此次使用的架构页版本为 `2026-07-28`；A2A 使用官方 `latest` 规范，页面包含 1.0 的接口与迁移说明。`latest` 会变化，实施时应锁定规范和 SDK 版本，检查迁移指南并测试双方支持的能力。不要把旧教程中的连接初始化、传输或字段示例直接混到另一版本。

MCP 可以在本地使用 stdio，也可通过 Streamable HTTP 访问远端服务；“一定是远端服务”“接上就能被所有客户端无差别使用”都不准确。接入前要核对认证、资源权限、错误语义和部署边界，尤其不能把工具返回的外部文本当作更高权限的指令。[MCP 安全实践](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

## 五 · Computer Use 的能力与边界

Computer Use 通过截图或界面状态感知环境，再执行点击、输入、滚动等动作。它使没有适用 API 的软件也可能被操作，但增加了位置变化、遮挡、加载等待和结果误判等问题。网页和图像中的恶意指令也可能影响模型；相关模型防护不能替代隔离环境和权限边界。[Computer Use 官方文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)

面向产品，应将一个操作拆成“观察 → 动作 → 重新观察 → 核验”。点击保存后，核对文件、成功状态或业务记录是否真的出现；不能把“点到了按钮”作为完成证据。有稳定 API 且授权适用时，通常优先考虑结构化接口；界面自动化适合填补接口缺口，并应为失败、接管和超时保留路径。

例如未来做“把学习计划填进学校系统”：先生成可审阅的计划，用隔离测试账号试填；提交前核对学生、课程、内容及授权；提交后读取状态确认。只有端到端成功率、错误代价和人工接管成本满足需求，才扩大使用范围。当前茶寮没有 Computer Use 执行能力。

## 六 · 本项目映射与下一阶段设计

| 当前代码 | 已实现 | 不能据此宣称 |
|---|---|---|
| `src/core/agent/orchestrator.ts` | 单次取证循环、重复调用检测、停止原因、生成与校验 | 能在服务重启后恢复原运行 |
| `src/core/agent/toolRegistry.ts` | 参数校验、工具限次、等待超时与 hooks | 业务授权、审批和副作用幂等已经齐全 |
| `src/core/agent/tools.ts` | 搜索、读取来源、显式结束；当前工具只读 | 已接入 MCP、A2A 或任意桌面操作 |
| `src/core/agent/transport.ts` | 适配不同模型的工具调用消息格式 | 它就是 MCP Client |
| `src/core/agent/types.ts` | 默认最多 6 个工具步骤、单次模型等待预算 45 秒、取证循环墙钟检查 90 秒 | 这些字段就是覆盖所有生成、摘要和重试的端到端硬截止时间 |

代码里的 `withTimeout` 通过计时器结束等待，没有传递取消信号给工具执行函数。因此它不能承诺底层工作随超时终止；引入写工具前应单独设计取消与结果核对。当前总时长检查主要位于取证循环，生成与校验重试另有路径，也不能把 90 秒直接当作产品 SLA。

## 七 · 落地练习：让茶寮发布学习计划

需求：用户让系统根据典籍生成一周学习计划，审阅后发布到个人学习空间。假设未来加入有副作用的 `publish_plan` 工具，接口可能超时。

请说明：什么用 workflow，什么交给 Agent；保存哪个检查点；审批绑定什么；超时后怎么恢复；是否必须引入 MCP 或 A2A。

**参考答案：** 资料取证可沿用受控 Agent；生成草稿、等待审批、发布和核对发布结果由明确工作流串联。草稿完成时保存产物编号与版本，审批后保存审批编号和待执行动作；发布用稳定幂等键。超时后查询发布状态，确认未提交且接口支持安全重试才重试，否则转人工核对。个人空间的现成 API 已能满足需求时，直接包装本地工具即可；MCP 用于实际存在的跨宿主复用需求，A2A 用于实际存在的 Agent 服务协作需求。

**自测：** 三个人设就是多 Agent 吗？不是。换更强模型就能断点续跑吗？不能。工具超时说明动作没发生吗？不能这样推断。
