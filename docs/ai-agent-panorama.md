# AI Agent 全景图：先定位，再选架构

看到一个 AI 产品，先问：它感知了什么、怎样表示信息、预测什么、由谁决策、如何行动？这是学习馆统一地图的第一层。完整路线见 [AI 五层学习地图](/learn/ai-learning-map)。

## 一 · 从信息到行动

```text
感知 → 表征 → 预测 → 决策 → 行动
  ↑                         │
  └────── 环境反馈 ──────────┘
```

这是分析系统的视角，不要求每个产品都有五个独立模块。例如文本生成模型把输入切成 Token、转换成向量表示、预测后续 Token；聊天应用再把结果显示给用户。Agent 系统接收目标和环境信息，根据当前状态选择工具，执行后检查结果，再决定继续、停止或交给人处理。

| 系统问题 | 天道茶寮中的例子 |
|---|---|
| 感知：拿到什么信息？ | 用户问题、问者档、已入库文档、工具结果 |
| 表征：信息怎么组织？ | 文本向量、按来源编号的证据台账、会话摘要 |
| 预测：模型输出什么？ | 下一个 Token、工具名与参数、回答文本 |
| 决策：谁控制下一步？ | 模型选择检索或精读；程序控制权限、限次与退出 |
| 行动：环境发生什么变化？ | 执行检索、读取原文、返回回答；当前取证工具以只读为主 |

预测一个工具调用只是提出行动建议。参数通过校验、运行时执行成功后，才真的发生了工具行动。

## 二 · LLM、RAG、Workflow、Agent 各在哪个抽屉

它们不是一条“必须不断升级”的产品等级线。

| 名称 | 概念类别 | 核心问题 |
|---|---|---|
| LLM | 模型类别 | 如何从上下文生成语言或结构化输出？ |
| RAG | 应用架构模式 | 如何检索外部资料来增强生成？ |
| Workflow | 流程编排方式 | 如何按预先定义的路径组织步骤与校验？ |
| Agent | 运行系统 / 软件架构 | 如何依据目标与环境反馈动态选择下一步？ |
| Multi-agent | 多智能体协作架构 | 如何让多个独立运行的 Agent 分工、交接和汇总？ |

固定 Workflow 可以包含 RAG；Agent 可以把检索作为工具；多个 Agent 也可以处于 Workflow 中。RAG 可以多次检索、改写查询、重排结果，定义没有规定“只能查一次”。Agent 也不必每个问题都调用很多工具。[RAG 原论文](https://arxiv.org/abs/2005.11401)讨论检索与生成的结合；[Anthropic 的架构说明](https://www.anthropic.com/engineering/building-effective-agents)按谁控制流程区分 Workflow 与 Agent。

选择应由任务决定：固定格式的分类或抽取可以先验证一次模型调用；资料问答考虑 RAG；步骤明确的业务考虑 Workflow；路径难以预先确定、又能获得可检查反馈时，再考虑 Agent。增加自主性和多个角色可能提高完成率，也可能增加延迟、费用和协调错误，需要评测证明收益。

## 三 · 天道茶寮当前实际实现

以下按当前源码核对；不是未来蓝图。

| 使用方式 | 实际路径 | 代码入口（位于 src/） |
|---|---|---|
| **循迹 · 开（当前默认）** | 受控 Agent 工具循环 → 证据台账 → 生成 → 校验 | `components/ChatPanel.tsx`、`core/agent/orchestrator.ts` |
| **循迹关闭** | 固定 RAG 链路 → 检索上下文 → 生成 → 校验 | `core/retrieval/answerWithCitations.ts` |
| 三贤对谈 | 同一轮生成任务按角色组织回应，使用分库规则与声口校验 | `data/mentors.ts`、`core/retrieval/voicePolicy.ts` |

三贤有角色分工，**当前并不是三个独立 Agent**。三段文字、三个人设、三个资料分区，都不能单独证明存在多智能体协作。

循迹的取证过程可能如下，每轮次数由结果与运行边界决定：

```text
问题 → search_library 查询相关材料
     → read_source_unit 核对命中来源的完整单元
     → 继续检索，或 ready_to_answer 声明收束
     → 从证据台账拼装 Sources
     → 生成角色回应 → 引用/声口校验 → 交付
```

工具注册表提供 `search_library`、`read_source_unit`、`ready_to_answer`。默认取证工具步数预算为 6，另有超时、重复调用检测、取消与收束条件；它不代表最多只能调用 6 次模型，也不代表 6 步内必定完成。细节见 [工具循环设计](/learn/agent-loop)。

RAG 能让资料更新与来源核对变得可行，但错误资料、漏检、误读和无依据推断仍会造成错误。本项目的引用校验主要核对出处及角色可用资料范围，不能自动证明每句话被原文支持。当前 RAG 可定向重试一轮，Agent 生成后可重试两轮，仍失败时可能带警告交付。读者应分清“有引用”“引用有效”“结论正确”。

## 五 · 自测

1. 从 PDF 抽取文字、生成 Embedding、预测工具参数、执行查询，各对应链路哪一环？
2. 为什么“RAG 是 Agent 的低级版本”不准确？同一产品能否同时使用两者？
3. 打开和关闭循迹，各由谁决定检索路径？
4. 把三贤拆成三个独立 Agent 前，应该测什么收益与成本？
5. 一条回答有真实书名和章节，是否足以说明结论正确？
