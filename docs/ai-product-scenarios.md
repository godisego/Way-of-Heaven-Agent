# AI 产品与业务场景

不是所有问题都值得用 AI。这篇教你判断"什么问题该用 AI""什么不该用""怎么衡量效果"——不学术，用开茶馆做类比。

> **前置**：读完 [AI Agent 全景图](/learn/ai-agent-panorama) 再来这篇更有感觉。

## 一 · 先问三个问题

拿到一个需求，先别急着选模型。问自己：

```
① 这个问题，规则能解决吗？
   ├─ 能 → 别用 AI，写 if-else
   ├─ 不能，但变化太多 → 考虑 AI
   └─ 不确定 → 先试规则，不行再上 AI

② 模型能做这件事吗？
   ├─ 需要推理/总结/生成 → 能
   ├─ 需要精确计算 → 不能（用计算器）
   └─ 需要实时数据 → 不能（用搜索 API）

③ 错了能接受吗？
   ├─ 错了就是删数据/花钱/伤人 → 必须有人工兜底
   ├─ 错了只是回复不够好 → 可以直接上
   └─ 错了不能发现 → 必须加校验
```

**天道茶寮的例子**：
- 排盘计算 → 规则能解决 → **不用 AI**，用确定性算法
- 解读命理 → 需要推理 + 引用典籍 → **用 RAG**
- 判断吉凶 → 错了可能伤人 → **强制人工边界**，不直断吉凶

## 二 · 什么问题适合用 AI

| 适合 AI | 不适合 AI | 例子 |
|--------|----------|------|
| 需要理解自然语言 | 需要精确计算 | "帮我算一下 1234 × 5678" → 用计算器 |
| 需要从大量文本提取信息 | 需要实时数据 | "现在比特币多少钱" → 用行情 API |
| 需要生成内容 | 需要唯一正确答案 | "1+1 等于几" → 用计算器 |
| 规则太多写不过来 | 规则简单明确 | "判断一个数是不是偶数" → 用 `n % 2` |
| 容忍一定错误率 | 不能容忍任何错误 | "控制红绿灯" → 用确定性系统 |
| 有反馈闭环能持续改进 | 一次出错全盘皆输 | "自动炒股" → 别用 AI |

### 天道茶寮的产品决策

```
用户需求："帮我解读八字盘"

拆解：
├─ 排盘：年月日时 → 天干地支
│  └─ 规则确定 → 确定性算法，不用 AI
├─ 查典籍：从命理书籍找相关内容
│  └─ 需要语义匹配 → RAG
├─ 生成解读：基于典籍 + 盘面给出建议
│  └─ 需要推理 + 个性化 → LLM 生成
├─ 校验引用：回答里的引用是否真实
│  └─ 确定性校验 → 程序校验，不用 AI
└─ 声口校验：老胡像不像老胡
   └─ 模式匹配 → 程序校验 + 重试
```

**关键洞察**：一个功能里，不是所有环节都要用 AI。把确定性的部分抽出来用规则，只在该用 AI 的地方用 AI。

## 三 · 衡量效果：ROI 怎么算

AI 不是免费的——每次调用都花钱（token 费），每次生成都有延迟。你得算账：

```
投入 = 模型调用费 + 开发时间 + 维护成本 + 服务器费
产出 = 节省的人力 + 提升的体验 + 新增的能力
ROI = (产出 - 投入) / 投入
```

### 天道茶寮的账本

| 项目 | 投入 | 产出 |
|------|------|------|
| 聊天 API | ~0.02 元/次（MiniMax） | 替代了一个 24h 在线的命理顾问 |
| Embedding | ~0.001 元/次（mock 免费） | 让检索能找到相关段落 |
| 开发时间 | ~3 个月（一个人） | 可复用的 Agent 学习场 + 命理工具 |
| 服务器 | Vercel 免费 tier | 足够个人使用 |

**ROI 判断**：如果天道茶寮是商业产品，每月 1000 次对话 × 0.02 元 = 20 元 API 费。替代一个 7×24 的命理顾问（月薪至少 5000），ROI 非常高。

### 但如果你的场景是：

```
场景：自动回复邮件
投入：API 费 + 开发 + 维护
产出：节省客服时间

如果每天只有 10 封邮件 → ROI 太低，不值得用 AI
如果每天有 1000 封邮件 → ROI 很高，值得
```

**关键指标**：量太小不要用 AI，规则能解决不要用 AI，错了不能改不要用 AI。

## 四 · 试点方法论

别一上来就全面 AI 化。先试点：

```
第一步：选一个低风险场景试点
  └─ 天道茶寮选了"命理问答"——错了不伤人，有引用可核对

第二步：定义成功标准
  └─ 引用准确率 >90%、角色声口通过率 >85%、资料不足时不编造 100%

第三步：跑 100 个真实问题
  └─ 看哪些走通了、哪些失败了、失败原因是什么

第四步：根据失败原因迭代
  └─ 检索不准 → 调 chunk / embedding
  └─ 引用不对 → 加校验
  └─ 角色跑偏 → 调 prompt

第五步：评估是否值得推广
  └─ 成本可接受？效果稳定？用户满意？ → 是 → 推广
  └─ 否 → 缩小范围或放弃
```

## 五 · 人工兜底

AI 会犯错。关键问题是：**错了怎么办？**

```
用户提问
  │
  ├─ AI 有信心（引用校验通过 + 声口通过）
  │   └─ 直接回答
  │
  ├─ AI 不太有信心（引用校验失败 或 声口失败）
  │   └─ 重试一次 → 还不行 → 返回"暂未入藏"
  │
  └─ AI 不该回答（高风险问题：吉凶断语、医疗法律）
      └─ 边界规则拦截 → 返回安全回应
```

### 三层兜底

| 层级 | 谁负责 | 做什么 | 天道实例 |
|------|--------|--------|---------|
| **第一层：程序校验** | 代码 | 引用校验、声口校验、边界规则 | 检查引用的书名是否真实存在 |
| **第二层：模型自纠** | LLM | 一次重试，修正问题 | 提示模型"你缺少引用，请补充" |
| **第三层：人工兜底** | 人 | 审查异常 case，更新规则 | 每周看一轮"暂未入藏"的问题，判断是否要加文档 |

**没有第三层的系统不是好系统**——你永远不知道用户问了什么你答不了。

## 六 · AI 功能 PRD 模板

写一个 AI 功能的需求文档，和普通 PRD 不一样，要特别说清楚：

```markdown
## 功能：XXX

### 场景
- 用户是谁？在什么场景下用？
- 天道实例：对命理好奇的普通人，想用八字工具了解自己

### 输入
- 用户输入什么？（文本？语音？图片？）
- 有什么约束？（长度限制？格式要求？）

### 输出
- 期望输出什么？（文本？结构化数据？）
- 格式要求？（引用格式？角色声口？）

### 边界
- 不能做什么？（不直断吉凶？不回答医疗？）
- 资料不足时怎么处理？（说"暂未入藏"）

### 成功标准
- 引用准确率 ≥ X%
- 角色声口通过率 ≥ Y%
- 资料不足时 100% 不编造
- 平均响应时间 ≤ Z 秒

### 兜底
- 程序校验失败 → 重试 → 还不行 → 安全回应
- 高风险问题 → 直接进入安全策略
```

## 七 · 自测

1. 什么问题适合用 AI？什么问题不适合？各举一个你的工作里的例子。
2. "排盘计算"为什么天道茶寮不用 AI？如果用 AI 会怎样？
3. ROI 怎么算？你的场景如果用 AI，投入和产出各是什么？
4. 三层兜底是哪三层？天道茶寮各做了什么？
5. 试点方法论的五步是什么？为什么不能一上来就全面 AI 化？
