# AI 产品与业务场景

模型能完成一次演示、工程能把它接进系统、用户愿意为结果付钱，是三个需要分别验证的问题。本课位于第五层“AI 产品思维”。前置：[五层地图](/learn/ai-learning-map)，进阶：[Solution / FDE 交付](/learn/ai-solution-delivery)。

## 一 · 先问三个问题

1. **原来的任务是什么？** 谁在什么场景做、怎样做、每次花多少时间、哪些错误最痛？
2. **模型适合承担哪一步？** 语言理解、分类、生成是候选；精确计算与已定义规则通常交给确定性程序，实时信息由授权数据接口提供。
3. **做错怎么办？** 分别定义漏报、误报、瞎编、越权的代价和发现方式，安排停止、补资料或人工处理路径。

“需要总结”不等于模型必然能做好，“实时数据”也不是整个 AI 产品的禁区：模型可以调用行情、库存等 API，但不能靠训练记忆提供当前事实。低风险任务也需要小规模验证，不能因为可撤销就直接全量上线。

## 二 · 拆一个真实功能

| 用户任务 | 适合的技术 | 验证点 |
| --- | --- | --- |
| 把年月日时换算成盘面 | 确定性算法 | 时间、地区、边界规则与已知样本 |
| 从资料找相关段落 | 检索 / RAG | 来源、召回、相关性、可访问范围 |
| 用易懂的语言解释资料 | LLM 生成 | 有依据、可理解、不添造事实 |
| 判断是否还要查原文 | 有限工具循环 | 工具参数、证据充分性、停止条件 |
| 检查引用位置是否合法 | 程序校验 | 来源台账与书名、章节匹配 |
| 整理用户投诉类别 | 分类器、LLM 或决策模型 | 每类误差、未知输入、校准、成本 |

天道茶寮把多种机制组合起来，并不意味着它验证了命理预测能力。产品学习价值可以来自术语解释、来源阅读和代码实践；不能用“替代一名专业顾问”的未经验证假设计算收入或省下的工资。

## 三 · ROI 不是只算 Token 费

```text
当前流程成本 = 人工时间 + 返工 + 系统成本
AI 方案成本 = 模型与工具 + 检索与存储 + 开发部署摊销
             + 监控维护 + 人工复核 + 错误造成的新增损失
净收益 = 可兑现的收益或节约 - AI 方案增量成本
ROI = 净收益 / 约定的投入基数
```

收益和投入必须采用相同时间窗口、明确是否包含一次性开发、说明节省工时能否兑现。每次调用便宜，不代表每个**成功完成的任务**便宜；多轮重试、失败任务、人工复核都会进入成本。

不要使用固定供应商单价、免费套餐或行业工资充当项目实测。价格和用量在试点时从实际合同及账单取数。本课程使用的完整假设账本见 [交付课的 ROI 练习](/learn/ai-solution-delivery)。

## 四 · 怎样试点

先选一个边界清楚、数据可获得、有人工基线的任务。用代表性样本评估规则、简单模型调用和复杂系统，记录哪些情况下简单方案已经够用。Workflow 与 Agent 对控制权和复杂度的取舍，可参考 [Anthropic 工程说明](https://www.anthropic.com/engineering/building-effective-agents)。

| 试点阶段 | 要完成的事 | 是否改变业务 |
| --- | --- | --- |
| 离线验证 | 固定测试集，比较基线与候选方案 | 不改变 |
| 影子运行 | 真实输入产生建议，与实际处理比对 | 不执行建议 |
| 辅助模式 | 工作人员看到建议并决定是否采用 | 由人确认 |
| 有限自动化 | 开放已验收的低风险动作 | 限队列、限权限、可退回 |

成功标准应是业务可判定的：严重投诉召回、有效引用比例、平均复核时间、任务 p95 延迟、每成功任务成本等。数值由业务基线与错误代价决定，不存在适合所有任务的“90% 就能上线”。

## 五 · 人工兜底必须是一条可执行路径

```text
输入与权限校验 → 获取资料 → 模型输出 → 程序与业务校验
                                              ↓
                           通过 → 执行授权范围内的动作
                           不通过 → 有界重试 / 补资料 / 转人工
```

“有信心”不能只看模型自报分数、引用格式或声口校验。引用位置合法，不代表引用支持结论；声口像某个角色，也不代表结论正确。不同验证器只能证明各自检查的那部分。

本项目已有来源与声口校验，但重试后仍可能带软警告返回回答，因此不能宣称所有错误都被拦截或“必然安全拒答”。项目的确定性检查与人工审阅如何分工，参见 [评测与可观测性](/learn/agent-evaluation-observability)。设计企业功能时要明确谁接手、多久处理、怎样恢复，以及异常怎样反馈给评测集。

## 六 · AI 功能 PRD 模板

```text
用户与场景：谁，在什么触发条件下，需要什么结果？
当前基线：任务量、耗时、错误类型、成本、用户满意程度。
AI 改变的步骤：输入、输出、数据来源、必要接口。
能力证据：使用哪个版本，在哪些样本上测过，哪些还没测？
权限与边界：能查什么、能改什么、何时需要人工确认？
验收标准：业务指标、分群误差、复核量、成本与尾延迟。
失败路径：缺数据、模型超时、工具失败、写入结果未知怎样处理？
试点计划：负责人、样本范围、退出条件、回滚与复盘方式。
价值证据：采用率、重复使用、节省是否兑现、付费意愿如何验证？
```

## 七 · 自测与参考答案

1. 从 100 篇反馈里总结不满原因、精确乘法、查询当前库存，分别怎样实现？
2. 模型费用降了 80%，为何项目仍可能亏？
3. 一份回答引用格式全部正确，是否可以取消业务审核？

**参考答案**：文本归纳可用模型并抽检，乘法用计算程序，库存取授权实时系统；人工复核、返工、部署和低采用率可能抵消费用降低；格式校验不验证事实支持、结论推理或业务授权，不能凭这一项取消必要的审核。

**阶段交付**：先填上面的 PRD 模板，每项写明“已测量 / 教学假设 / 待验证”；至少采访一名实际执行者，或在练习中明确采用虚构角色。完整填写示例、失败用例和评分标准见 [毕业项目](/learn/ai-capstone)。没有真实访谈时，不把代写的用户意见当需求证据。
