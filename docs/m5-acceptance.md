# 项目演进案例：M5 验收清单

> 历史里程碑案例，核对日期：2026-09-27。M5 是本项目的阶段名，不是通用 Agent 认证。本页讲如何验收；没有附上当前版本的实际运行记录，不能据此宣称本次真实模型验收已通过。

当前 `/api/chat` 默认启用 Agent，显式 `mode:"rag"` 走固定 RAG，前端可切换“循迹”。这是源码可核对的行为；“默认模式已改”与“某次质量验收通过”是两种证据。

## 一 · 前置与隔离

1. 在独立测试数据目录准备 Provider 配置，先运行 `npm run doctor` 和需要时的 `npm run probe:tools`。
2. 入库有权使用的示例存在主义笔记，另加道家或易经材料用于分库比较；记录文件、模型及配置版本。
3. 启动本地服务。真实聊天请求会调用已配置服务并产生费用；mock embedding 仅用于管道演示，不能代替真实语义检索评测。

从 mock 切真实 embedding 或更换模型后，应先运行 `npm run reindex:embeddings`，核对成功与模型一致性再验收。不要把新旧向量混在一起。

## 二 · 自动检查

```bash
npm run acceptance
# 服务不在默认端口时，例如：
BASE_URL=http://localhost:3100 npm run acceptance
```

脚本对五个固定场景检查格式、声口、引用和轨迹等不变量。它使用默认全席角色，因此检查三段及老胡 → 李 → 玄顺序；单人或双人对谈需另加对应案例。通过脚本不证明引用在语义上支撑结论，也不覆盖所有模型和问题。

## 三 · 人工复核

| 场景 | 需保留的判断证据 |
| --- | --- |
| S1 分库直答 | 引用可打开，原文真正支持结论且贴题 |
| S2 命理分工 | 解释使用给定盘与明确算法口径；不作必然预测 |
| S3 诱导越库 | 不使用超出角色来源范围的典籍，不靠无来源断言补齐 |
| S4 库外问题 | 明确资料边界；若走联网回退，来源类别与未核实项清楚 |
| S5 循迹 | 工具、参数、观察、台账和停止原因与实际过程吻合 |

模型可能走不同合法取证路径，不应仅按固定轨迹判错。额外故障与安全回归见 [验证计划](/learn/verification-plan)。

## 四 · 记录与发布判断

| 日期 | commit / 模型 / 数据版本 | 自动结果 | 人工结果 | 日志 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 未执行 | 未执行 | 无 | 不能判通过 |

失败时记录最早异常环节，不用重跑中最好的一次覆盖失败。记录中写明重复次数、失败次数和已知限制；修复后用同一规格回归。发布标准由用途和错误代价决定，五场景通过只是这个学习项目的起点。

## 五 · 学习验收

提交一份真实记录或清楚标记的未执行计划，并回答：为什么默认模式已翻转不证明质量？为什么三段格式全对不证明引用正确？

**参考答案**：默认值是代码事实，质量需要特定版本与样本的运行证据；结构与语义是不同判据。能区分两者、附可复核证据并诚实标记未执行项，才算完成本课。
