# LLM 基础原理速览

这篇属于五层地图的**第三层：模型原理**。先建立直觉，再进入 [Transformer 与 Attention](/learn/transformer-mechanics)。本项目调用模型服务，没有在仓库内训练或实现 Transformer。

## 一 · 从输入到下一段文字

以常见的自回归文本模型为例：

```text
输入文字 → Tokenization → Token ID
         → Embedding + 位置信息
         → 多层 Transformer 计算
         → 下一个 Token 的概率分布
         → 按解码策略选取 Token → 继续生成或结束
```

“预测下一个 Token”描述生成机制，并不意味着模型只能完成简单续写。训练使模型学到语言和模式，后训练进一步调整指令遵循等行为；最终能力仍需在任务上验证。一个聊天产品还可能包含搜索、工具、记忆等模块，不能用单个模型的生成步骤解释全部产品行为。

## 二 · Token 不是“一个汉字”

Token 是分词器处理的单位，可能对应一个字、词的一部分、标点、空格或字节片段。**中文字数与 Token 数没有固定换算比率**；它取决于 tokenizer、语言、具体内容与特殊标记。

同一段中文，用不同模型的 tokenizer 统计，结果可能不同。代码、罕见字符和混合语言也会改变比例。不要背“一个中文字等于 1～2 个 Token”或某个短句固定多少 Token；应使用目标模型的计数接口或 tokenizer 做测量。模型计费、窗口预算和输出上限通常都以 Token 计。

本项目 `mockEmbeddingProvider.ts` 用中文字符二元组辅助哈希检索。那是本地模拟检索的分词策略，**不是聊天模型的 tokenizer**。

## 三 · Embedding、Attention 和 Transformer

| 模块 | 直觉 | 不要混淆 |
|---|---|---|
| Token Embedding | 把 Token ID 映射成可计算的向量 | 不等于本项目用于整段资料检索的 Embedding API |
| 位置信息 | 让模型区分顺序和位置关系 | Attention 本身不能凭空知道句子顺序 |
| Attention | 根据当前表示，从可见位置读取加权信息 | 权重不能直接视为完整、忠实的决策解释 |
| FFN | 对每个位置的表示继续做非线性变换 | Transformer 并非只有 Attention |
| Residual / Norm | 帮助信息传递与训练稳定 | 具体模型的归一化方式、顺序会有差异 |

例如“他把资料交给小林，因为小林要写报告”，当前 Token 的表示会利用前面的相关信息。Q/K/V 是计算相关性并汇总信息的三个投影；不要把它们理解为模型外接的数据库。公式和带因果掩码的例子见 [Transformer 讲义](/learn/transformer-mechanics)。基础架构来自 [Attention Is All You Need](https://arxiv.org/abs/1706.03762)。

## 四 · 训练和推理分别在做什么

| 阶段 | 做什么 | 是否通常修改模型参数 |
|---|---|---|
| Pretraining 预训练 | 从大量训练数据学习统计结构与能力 | 是 |
| SFT 监督微调 | 用任务示例调整行为 | 是 |
| 偏好优化 / 强化学习等后训练 | 使用偏好或奖励信号进一步调整行为 | 通常是 |
| Inference 推理 | 用当前参数处理输入并生成输出 | 通常否 |

RLHF、RLAIF 描述反馈来源的不同，不意味着所有模型都采用相同训练配方。Prompt、RAG 和会话摘要通常是在推理时提供上下文，并不自动把知识写进模型权重。多聊几轮也不等于模型对你完成了微调。

## 五 · 上下文窗口和输出预算

上下文窗口限制一次模型计算可使用的信息量。需要考虑系统指令、历史消息、检索片段、工具定义、工具返回，以及为输出预留的空间。不同 API 对输出和推理 Token 的预算规则可能不同，要按具体接口核对。

```text
可用资料预算 ≈ 可用上下文容量 − 指令 − 历史 − 工具内容 − 输出预留
```

这是规划用的近似式，不是跨厂商统一的计费公式。窗口够大也不代表模型能可靠利用其中每一处细节；堆更多材料可能带来噪声、冲突和延迟。因此要筛选、去重、保留来源，并在必要时摘要或重新检索。

天道茶寮的 `core/conversation/contextBuilder.ts` 实现“历史滚动摘要 + 最近消息”；`core/agent/evidenceLedger.ts` 管理取证材料。它们属于应用的上下文工程，不是模型架构。继续读 [上下文与记忆工程](/learn/context-memory-engineering)。

## 六 · 温度控制采样，不是真实性开关

在支持 temperature 参数的模型中，较低温度通常使输出选择更集中，较高温度使选择更多样。参数范围、默认值和是否允许设置因模型而异。

**temperature=0 也不保证每次输出完全一致；降低温度更不保证事实正确。** 如果最可能的回答本身就是错的，低温度也可以稳定地产生错误。[Claude API 参数说明](https://platform.claude.com/docs/en/api/messages/create)明确说明零温度不等于完全确定。

本项目当前聊天 Provider 请求没有显式设置 temperature，因此不能声称“三贤靠低温防幻觉”。工程上应记录模型版本、采样配置、输入与重试过程，再通过评测比较准确率和稳定性。

## 七 · 幻觉如何减少，边界在哪里

幻觉指生成内容与事实或所给依据不一致，例如编造章节、误述数字、把猜测写成确定事实。它可能来自知识缺失、训练偏差、检索失败、上下文冲突或生成错误，不能只归结为“模型不知道自己不知道”。

| 措施 | 能帮助什么 | 不能保证什么 |
|---|---|---|
| RAG | 提供当前或私有资料，允许追溯 | 检索一定命中、资料一定正确、模型一定读对 |
| 引用校验 | 检查出处标记能否匹配允许来源 | 每句结论都被原文支持 |
| 工具计算 | 把精确计算交给程序 | 工具参数正确、结果解释正确 |
| 定向重试 | 根据具体错误修正输出 | 再次生成必定成功 |
| 拒答 / 人工复核 | 在证据不足或高代价场景控制交付 | 不必再评估漏答和复核成本 |

本项目既有 RAG 又有 Agent 取证路径，均做引用和声口校验。重试后仍可能带警告交付，不能把现有实现描述为“自动消除幻觉”。详见 [引用校验](/learn/citation-design)。

## 八 · 模型与运行系统的交界

Function Calling / Tool Use 让模型返回工具名和结构化参数。模型提出意图，运行时代码校验、执行，再把结果作为下一步输入。参数符合 JSON Schema，只能说明形状满足约束，不能说明查询条件、业务判断或权限正确。

```text
模型：search_library({"query":"自由与选择"})
运行时：检查参数、工具权限和调用预算 → 执行检索
模型：读取工具返回 → 继续选择工具或生成答案
```

聊天 Provider 负责生成；Embedding Provider 负责向量化。本项目两者可独立配置，未配真实 Embedding 时可用本地哈希模拟。模拟模式能验证链路，不能据此宣称语义检索质量达标。

部署模型可以选云端服务或本地运行，选择取决于数据要求、质量、成本、延迟与运维能力。本地运行仍有硬件和能源成本，是否离线或数据不外发取决于整个应用配置；不能仅凭“本地模型”就下结论。
