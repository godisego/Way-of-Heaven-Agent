# LLM 基础原理速览

你大概用过 ChatGPT 或类似的产品——输入一句话，它回一段话。但"它"到底在干什么？这篇不读代码、不碰数学，只说清楚几件你必须知道的事。

> 速查：[RAG](/learn/rag-concepts) · [幻觉](/learn/llm-fundamentals) · [Agent](/learn/agent-walkthrough)

## 一 · LLM 在做什么

大语言模型（LLM）= **一个读过海量文本、能预测"下一个字应该是什么"的程序**。

你输入"天行健"，它预测下一个字大概率是"君"；再下一个是"子"；再下一个是"以"——如此反复，一个字一个字蹦出来，连成一段话。

```
你输入：天行健
模型预测：君（概率 92%）
继续预测：以（概率 88%）
继续预测：自（概率 85%）
继续预测：强（概率 90%）
继续预测：不（概率 87%）
继续预测：息（概率 93%）
```

**这就是"生成"——每次只预测一个 token，串起来就是回答。**

## 二 · Token：模型眼里文本的最小单位

模型不是按"字"读文本的，是按 **token** 切。一个中文字大约 1~2 个 token（英文更省）。

```
"天行健君子以自强不息" ≈ 12 tokens
"I love you" = 4 tokens
```

## 三 · 上下文窗口：模型一次能读多少

每个 LLM 都有一个**上下文窗口**（context window）：一次调用能塞进去的最大 token 数。

| 模型 | 上下文窗口 | 大约能装 |
|------|-----------|---------|
| DeepSeek V3 | 128K tokens | 约 10 万字 |
| GLM-4.6 | 200K tokens | 约 15 万字 |
| GPT-5 | 400K tokens | 约 30 万字 |
| Claude Fable 5 | 1M tokens | 约 75 万字 |

> 注：数字随版本更新会变。一个明显的趋势是——**2026 年的主流旗舰模型（GPT-5.6 / Claude Fable 5 / GLM-5.2）上下文窗口已普遍达到 1M（百万 token）**，相比两年前 GPT-3.5 的 4K 扩大了约 250 倍；也有 DeepSeek V3 这类仍在 128K 档的。

**上下文窗口 = 模型的"工作记忆"**。你问一个问题、模型回答——这一来一回的全部文本，不能超过这个窗口。

RAG 检索回来的 topK 段落要拼到 prompt 里——如果段落太长，超出窗口，模型就读不全。这就是为什么 chunking 要把文档切成小段、topK 不能设太大。

## 四 · 温度：模型有多"敢冒险"

**温度**（temperature）是模型生成时的随机性参数：

| 温度 | 行为 | 适合 |
|------|------|------|
| 0 | 每次都选概率最高的 token——最保守、最稳定 | 事实问答、代码生成 |
| 0.7 | 偶尔选概率稍低的 token——有些变化 | 日常对话、创意写作 |
| 1.0+ | 更大胆地选低概率 token——更有创意、更不可控 | 头脑风暴、文学创作 |

天道茶寮的三贤对谈用较低温度——因为需要稳定引用典籍、不能瞎编。如果是玄道长谈气机，可以稍高一点。

## 五 · 幻觉：模型最大的毛病

**幻觉**（hallucination）= 模型自信地编造不存在的事实。

```
问：《存在与虚无》第 42 页写的什么？
模型：《存在与虚无》第 42 页讨论了自欺的概念……
（实际：模型根本没读过这本书，42 页是编的）
```

为什么会幻觉？因为模型的本质是"预测下一个 token"——它不知道自己"不知道"，只会按概率继续生成。如果它训练时见过类似句式，就会编出看起来很像真的内容。

**RAG 怎么解决幻觉**：不让模型靠记忆答，而是先检索真实段落拼到 prompt 里，让它"照着资料答"。再加上引用校验——如果它编了资料里没有的内容，程序会检测到并要求重写。

## 六 · Function Calling：模型怎么"调工具"

模型本身只会生成文本。但它可以生成一段 **JSON**，告诉框架"请帮我调这个函数"：

```
模型输出：
{
  "tool": "search_library",
  "arguments": { "query": "天干地支" }
}

框架执行：真的去向量库搜"天干地支"
框架把结果喂回给模型：找到了这些段落……
模型继续：好，我再看看够不够……
```

**关键区别**：模型不直接执行函数，它只生成"调用意图"。框架（你的代码）才真正执行。这避免了模型说"我帮你查完了"但其实什么都没做。

## 七 · Provider：谁来提供模型服务

调用 LLM 有两条路：**云端 Provider**（把请求发给别人的服务器）或**本地自托管**（把模型下载到自己机器上跑）。多数人用云端，但本地跑也越来越常见：

| Provider 类型 | 例子 | 天道茶寮怎么配 |
|--------------|------|-------------|
| OpenAI 兼容 | OpenAI、智谱、百川 | `OPENAI_COMPAT_BASE_URL` |
| Anthropic 兼容 | Anthropic、MiniMax | `CHAT_BASE_URL` + protocol=anthropic |
| **本地自托管** | Ollama、LM Studio、vLLM | 同样走 OpenAI 兼容，把 `OPENAI_COMPAT_BASE_URL` 指向 `http://localhost:11434/v1` |

**本地自托管**值得一说——用 [Ollama](https://ollama.com)、LM Studio 这类工具，可以把模型直接下载到自己电脑上跑。好处是**数据不出本机、完全免费、能离线**；代价是**非常吃硬件**：

- 跑得动的"小"模型（7B~8B 参数）也要 **8~16 GB 显存**；
- 大模型（70B 级别）得上专业显卡，甚至多张卡；
- 普通笔记本、集显虽然能跑起来，但**吞吐很慢**——每秒蹦出几个字，体验远不如云端。

一句话：**追求速度和质量，首选云端；在意隐私、想免费尝鲜、愿意折腾硬件，才考虑本地。**

天道茶寮把聊天和 embedding 拆成两个独立 provider：
- **聊天 provider**：负责生成回答（你的问题 → 模型生成三贤回应）
- **Embedding provider**：负责把文本变向量（用于检索）——没配时自动用 mock

两个 key 完全独立。配了聊天就能对谈，配了 embedding 检索更准。

## 八 · 把这些概念连起来

现在你能看懂这个完整流程了：

```
你的问题："天干地支是什么"
    │
    ├→ [Embedding] 把问题变向量
    ├→ [向量检索] 从知识库找最相关的 topK 段落
    ├→ [拼上下文] 把段落塞进 prompt（受上下文窗口限制）
    ├→ [LLM 生成] 模型基于段落生成回答（低温度防幻觉）
    ├→ [引用校验] 检查回答里的引用是否真的在检索到的段落里
    └→ 如果校验失败 → [重试] 把问题反馈给模型重写
```

每一步都在上面讲过了。**这就是 RAG 的完整链路**——天道茶寮「循迹」模式走的就是这条线。

Agent 模式在此基础上加了一层：把"检索一次"改成"模型自己决定调几次、调什么工具"——但底层还是上面这套。
