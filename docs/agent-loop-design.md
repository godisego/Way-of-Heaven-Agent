# 工具循环：运行机制与设计演进

> 当前实现走读，源码核对：2026-09-28。前置：[Agent 基础](/learn/agent-walkthrough)、[API 集成](/learn/api-integration)、[引用校验](/learn/citation-design)。本篇替换最初的 Phase 2 待评审草案；阶段建设思路见[项目蓝图](/learn/agent-blueprint)，验收规格见 [M5 案例](/learn/m5-acceptance)。

## 一 · 运行系统负责什么

模型提出工具调用，运行系统校验参数、执行工具、记录结果和限制预算。模型根据观察继续选择动作，取证结束后再生成回答。

```text
问题 + 会话上下文
        ↓
调度模型选择工具 → 注册表校验与执行 → 观察 + 证据台账
        ↑                                  │
        └──────── 未停止则继续 ─────────────┘
        ↓ 停止取证
根据台账生成在席角色回答 → 引用与声口检查 → 限次修正
        ↓
返回回答、引用、执行轨迹；API 保存会话
```

会话历史帮助理解追问；本轮可引用的典籍证据来自检索和台账。模型的自报“足够”不是事实验证。

## 二 · 三个工具与各自边界

| 工具 | 职责 | 当前限制 |
| --- | --- | --- |
| search_library | 检索藏书，返回证据条目 | 每轮最多 4 次，等待超时默认 15 秒 |
| read_source_unit | 读取已见文档的一个来源单元 | 每轮最多 3 次，等待超时默认 5 秒；文档 ID 必须已由检索返回 |
| ready_to_answer | 报告证据是否足够及缺失项 | 编排器识别后结束取证，不是执行有副作用的业务操作 |

参数 schema、次数限制和实现见 `src/core/agent/tools.ts`、`toolRegistry.ts`。文档 ID 范围能限制模型随意猜 ID，不能替代多用户鉴权。思想传统标签同样不是租户访问控制。

台账见 `evidenceLedger.ts`：去重、分配证据编号、保存来源坐标与文本，为生成和引用核验提供依据。登记了证据不保证回答的每项结论都被原文支持。

## 三 · 停止条件与预算

默认值来自 `src/core/agent/types.ts`；执行判断在 `orchestrator.ts`。

| 条件 | 实际含义 |
| --- | --- |
| maxSteps = 6 | 最多六次进入注册表执行的工具调用；不是整个请求最多六次模型调用 |
| modelCallTimeoutMs = 45000 | 调度模型请求的超时设置；异常进入失败处理，不保证自动再调用一次 |
| totalTimeoutMs = 90000 | 在取证循环边界检查经过时间；不是覆盖后续生成、重试与全部 IO 的硬截止 |
| repeated_call | 重复工具及参数触发停止，避免无效循环 |
| ready / insufficient | 模型通过收尾工具自报证据状态 |
| no_tool | 调度模型没有返回工具调用；裸文本不直接作为最终答案 |
| cancelled / failed | 取消或异常路径；需分别查看轨迹与最终状态 |

工具等待用超时竞争返回，不保证底层网络或计算已经取消。完整超时设计还要让下游支持 AbortSignal，并把剩余预算传到各阶段；这属于扩展工作。

## 四 · 生成、校验和反馈修正

生成使用台账整理出的来源与角色指令。引用校验核对来源坐标及角色范围；声口校验检查格式和预设规则。Agent 生成最多两次定向重试，固定 RAG 路径最多一次，不能混为一个全局重试次数。

反馈修正不等于重新训练模型，也不等于已实现跨任务 Reflexion 记忆。检查通过说明满足这些规则，不证明全部事实正确；残留问题可能作为警告交付，读者仍需核对原文。

## 五 · 如何读执行轨迹

记录工具、参数、观察、证据变化、耗时和停止原因，不需要展示模型私有思维链。依次问：

1. 本轮目标是什么，模型有没有选错工具？
2. 参数是否合法，查询是否有信息增益？
3. 工具结果是有效观察、空结果还是故障？
4. 台账是否有新增证据？停止是否合理？
5. 最终回答是否得到证据支持？规则警告是否清楚展示？

当前有会话持久化、滚动摘要、流式入口和保存的轨迹；最早设计里“以后再做”的这些项目不再代表现状。跨会话长期记忆、可恢复后台任务、多用户隔离和有副作用工具的幂等恢复仍需独立建设。最新总体边界见[架构总览](/learn/architecture)。

## 六 · 练习与判定

用脚本化 transport 依次模拟：一次搜索后收尾、重复同一查询、工具超时、非法参数、取消。提交输入、预期停止原因、真实轨迹及差异，不调用真实客户系统。

**参考要点**：正常路径应能从证据编号追到来源；重复调用应停止；超时应记录错误且不假定底层取消；参数错误不得执行工具；取消应有明确状态。比较 `orchestrator.test.ts`、`toolRegistry.test.ts` 中的断言，再给至少一个尚未覆盖的失败场景。通过标准是能解释一条实际轨迹和一个失败原因，而非背出六个组件名。
