# Agent 轨迹调试：失败到底发生在哪一层

Agent 出错时，最没用的问题是“模型为什么这么笨”。可调试的问题应该是：输入错了、工具没给够、工具描述误导、观察丢信息、停止条件过早，还是最终校验没兜住？

本项目打开“循迹”后，每轮回答附一份 trace。它不是模型完整思维过程，而是**可审计的动作记录**：调用了什么、参数是什么、工具返回了什么、登记了哪些证据、为何停止。

## 一 · 先把一次运行切成六层

| 层 | 关键问题 | 对应代码 |
| --- | --- | --- |
| 请求 | 问题、模式和用户档是否正确进入 | `src/app/api/chat/route.ts` |
| 调度 | 模型选择了哪个工具与参数 | `src/core/agent/orchestrator.ts` |
| 执行 | 参数是否合法、工具是否超时或失败 | `src/core/agent/toolRegistry.ts` |
| 观察 | 工具结果是否足够清楚地返回模型 | `src/core/agent/tools.ts` |
| 台账 | 证据是否去重、编号、保留出处 | `src/core/agent/evidenceLedger.ts` |
| 答案 | 引用、角色声口与重试是否通过 | `src/core/retrieval/answerWithCitations.ts` |

调试时从上到下找第一处异常。后面的错误经常只是前面错误的回声。

## 二 · 一步 trace 应该怎么看

每一步至少关注：

1. **tool**：选择了 `search_library`、`read_source_unit` 还是 `ready_to_answer`。
2. **arguments**：查询词、topK、传统标签、文档与页码是否合理。
3. **observation**：工具是返回证据、空结果还是结构化错误。
4. **evidenceIds**：本步新增了哪些 `ev_N`。
5. **duration / error**：是否触发超时或参数校验。

只看最终答案会把检索问题误判成生成问题；只看工具名又会漏掉“工具选对、参数选错”。

## 三 · 常见失败模式对照表

| 症状 | 第一检查点 | 常见原因 | 修复方向 |
| --- | --- | --- | --- |
| 一次检索就宣布够了 | `ready_to_answer` 前的台账 | 调度提示词过度鼓励尽快停止 | 增加证据充分条件或评测题 |
| 反复搜同一句 | 重复调用停止原因 | 模型看不懂空结果或工具描述 | 改观察文案；保留重复调用刹车 |
| 搜到相关书却答错位置 | evidence 条目与 cite_as | chunk 出处元数据丢失 | 修摄取与台账，不先改提示词 |
| 找不到明明存在的内容 | query、topK、embedding 模式 | 查询词过窄或 mock 语义弱 | 改写 query；用真实 embedding 对照 |
| 跨库引用 | tradition 与发言角色 | 检索过滤或引用校验缺口 | 检查分库结果和 citationPolicy |
| 三人说成一种口吻 | draft 与 voice violations | 人设输入或材料隔离失效 | 检查三件套、简报分发和声口规则 |
| 死循环 / 花费失控 | stopReason 与 step 数 | 无次数、超时或重复调用检测 | 先补刹车，再提高能力 |

## 四 · 空结果不是工具失败

搜索返回 0 条意味着工具执行成功，但当前查询没有召回证据。调度者应决定：

- 改写关键词再搜一次。
- 放宽或调整 tradition。
- 如果已有文档线索，精读来源单元。
- 如果问题本就超出知识库，明确资料不足并停止。

把空结果当异常重试，会造成循环；把空结果当“没有答案”的最终证明，又可能过早停止。观察文本必须帮助模型区分这两者。

## 五 · 错误观察为什么要喂回模型

工具参数由 zod 校验。参数不合法时，注册表不会让程序崩溃，而是把字段级错误变成观察返回调度模型。这样模型有一次机会修正调用。

但修正仍计入步数，因为错误调用同样消耗时间和 token。受控 Agent 的原则不是“永不出错”，而是“错误可见、可恢复、恢复有预算”。

## 六 · 证据台账怎样阻止来源漂移

工具结果登记为 `ev_1`、`ev_2` 后，起草上下文只从台账重建。调度模型不能在工具阶段看到一段话，起草阶段再凭模糊记忆重新编出处。

检查台账时问：

- 相同 chunk 是否重复登记。
- 每条是否保留 documentId、pageNumber、书名和 sectionTitle。
- 300 字预览是否截断了关键限定语。
- 精读结果是否仍指向允许读取的白名单文档。

## 七 · 六个停止条件分别防什么

1. 最大步数：防无尽探索。
2. 单次模型调用超时：防一个请求挂死。
3. 全程超时：防每步都合法但总体过慢。
4. 同参数重复调用：防无信息增益循环。
5. `ready_to_answer`：给模型正常收束出口。
6. 裸文本不作为最终答案：防调度阶段越权直接写稿。

停止原因本身是评测指标。大量运行都因“最大步数”停止，通常说明工具、观察或收束条件有系统性问题。

## 八 · 最小调试流程

1. 固定一个问题和一份知识库快照。
2. 保存完整 trace 与最终答案。
3. 找第一处不合理动作，不同时改三层。
4. 只修改工具描述、参数约束、观察文案或停止条件中的一项。
5. 用同题回归，再跑一组反例。
6. 将问题加入固定评测集，避免以后复发。

这比反复“优化 prompt 让它聪明一点”慢半步，却能留下工程证据。

## 九 · 三个练习

### 练习 A：资料不足

问一个知识库完全没有的主题。合格 trace 应显示搜索尝试、无证据或证据不足、正常停止；最终不应伪造引用。

### 练习 B：需要精读

问一个答案分散在同一章节前后的问题。观察调度者是否先搜索定位，再用 `read_source_unit` 读完整来源单元。

### 练习 C：跨库诱惑

让李解释《周易》并要求引用。合格系统可以谈现实选择，但李不能越权引用老胡专库；引用校验应拦截跨库来源。

## 十 · 从调试走向评测

一次 trace 解释“这次为什么错”；评测集回答“改动后整体是否更好”。把每次真实失败归入以下指标：工具选择正确率、证据召回率、引用有效率、跨库违规率、声口违规率、停止原因分布和成本延迟。
