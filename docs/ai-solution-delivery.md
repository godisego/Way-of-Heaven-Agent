# 从 AI 产品到 Solution / FDE 交付

读完这一课，你应能把“做一个 Agent”改写成一个可以试点、可以验收、也可以被证据否定的业务方案。前置：[产品与场景](/learn/ai-product-scenarios)、[评测与可观测性](/learn/agent-evaluation-observability)。

## 一 · 先分清三件事

**模型能力、系统可行性、付费价值是三项不同证据。** 模型能给投诉打标签，不代表它已接通企业工单系统；系统能接通，也不代表用户愿意改变流程或为它付钱。AI PM、Solution、FDE 的职责边界会因组织而异，本课用它们代表需求验证、方案设计和现场交付三种工作。

| 工作 | 必须回答 | 可检查的产物 |
| --- | --- | --- |
| 需求验证 | 谁遇到什么痛点，今天怎样处理？ | 用户访谈、当前流程、耗时和错误基线 |
| 方案设计 | AI 改变哪一步，与哪些系统连接？ | 数据流、接口契约、权限、失败路径 |
| 现场交付 | 在客户真实约束下能否持续使用？ | 测试集、集成记录、运行手册、验收报告 |

## 二 · 把需求写成可证伪的句子

差的命题：“我们做一个客服 Agent。”

可检验的命题：“一线支持人员每天花时间判断投诉优先级。先在一个已授权的历史工单队列上比较规则、LLM 和决策模型，目标是减少人工分流时间，同时使严重投诉漏报不劣于当前人工基线。试点先输出建议，验收后才讨论自动分配。”

明确填写：用户、触发场景、原流程、当前成本、AI 替代步骤、错误类型、错误代价、验收人、付费或采用证据。不要把“准确率达到 95%”单独当需求：如果严重投诉只占 1%，全部判普通也会有 99% 的总体准确率。

## 三 · 用同一套任务比较候选方案

| 方案 | 适合承担的环节 | 试点需要测什么 |
| --- | --- | --- |
| 规则 / SQL | 超时次数、已验证状态等确定条件 | 覆盖率、规则维护与漏报 |
| 传统分类器 | 标签稳定、有足够标注数据的任务 | 分布变化、召回与校准 |
| LLM + 结构化输出 | 需要语言理解、少样本适配的分类或草稿 | 格式有效性、判断正确性、延迟与成本 |
| Jev 等类型化决策模型 | 有限选项、评分或概率判断 | 分类质量、校准、误报漏报、服务表现 |
| Workflow | 已知固定步骤与审核点 | 端到端成功、重试与一致性 |
| Agent | 调查路径取决于工具反馈 | 任务完成、工具行为、预算和可恢复性 |

这些方案可以组合；表格不是性能排名。必须在同一数据、同一权限、同一完成标准下比较。供应商测试只能支持候选筛选，不能替代客户验收。[Jev 专篇](/learn/jev-decision-models) 解释其发布声明与适用边界。

## 四 · 交付图必须画到失败路径

```text
工单事件 → 校验身份与字段 → 拉取授权历史 → 规则预筛
                                         ↓
                                模型给出分类与概率
                                         ↓
                         阈值策略 + 业务规则 + 权限检查
                           ↓                       ↓
                       分配建议                 人工复核
                           ↓                       ↓
                         确认 → 工单 API → 查验写入结果
                                      ↓
                             记录版本、耗时与处理反馈
```

缺历史资料时，记录缺失并转复核；模型接口超时，走原有人工队列；写入请求超时，先用业务唯一标识查询结果，再决定是否重试。模型分数不能代替权限校验。学习馆当前没有接入 Jev 或企业工单系统，这是一份设计练习。

## 五 · 用一笔完整账验算

以下数字全部是**教学假设**，不代表任何供应商报价或本项目经营数据。统一按每月 10,000 张工单、每分钟人力成本 1 元计算。

| 项目 | 算法 | 金额 |
| --- | --- | --- |
| 原人工分流 | 10,000 × 3 分钟 × 1 元 | 30,000 元 |
| AI 后抽检与复核 | 10,000 × 0.8 分钟 × 1 元 | 8,000 元 |
| 模型与工具 | 当月实际账单，假设 | 2,000 元 |
| 维护与部署摊销 | 当月分摊，假设 | 5,000 元 |
| 新增误分返工 | 100 单 × 20 元，假设 | 2,000 元 |
| AI 方案合计 | 8,000 + 2,000 + 5,000 + 2,000 | 17,000 元 |

月度净节约 = 30,000 - 17,000 = 13,000 元。若本练习把 17,000 元的新增方案成本作为 ROI 分母，则 ROI = 13,000 / 17,000 ≈ 76.5%。采用其他财务口径时写清分母，避免不同项目数字无法比较。

节省工时不等于实际现金流，更不等于收入。只有释放的时间被用于可确认的产出或减少真实支出，才能兑现收益。若复核时间变成每单 2.5 分钟，合计成本变为 34,000 元，净节约为 -4,000 元，原方案就不成立。

还应单独报告重大漏报等尾部损失，不能用平均返工费稀释。这些教学数值只训练算账方法，不构成投资或行业建议。

## 六 · 试点的五份交付物

1. **需求与基线页**：当前流程、代表性样本、任务量、耗时、用户采用意愿。
2. **方案页**：系统边界、模型版本、数据来源、接口、权限、失败恢复。
3. **验收集**：正常、模糊、缺资料、长文本、攻击文本、服务超时；测试集与调参集分开。
4. **运行手册**：负责人、告警、人工接管、退回原流程、事件记录和版本回滚。
5. **结果报告**：完成任务数、各错误类型、人工复核比例、p95 延迟、每成功任务成本、净收益与局限。

验收阈值应由业务负责人基于基线和错误代价共同确定。先影子运行，再小范围辅助，再按证据开放自动动作。不要仅凭一段演示或一次平均分就扩大范围。把业务目标、测量和风险处置连起来的思路，也可参考 [NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)；这里的五份交付物是教学模板。

## 七 · 练习与参考答案

**练习**：模型把总体准确率从 94% 提高到 97%，却把严重投诉召回从 96% 降到 80%，人工复核耗时也翻倍。能宣布试点成功吗？至少提出三项下一步。

**参考答案**：不能。先核对严重投诉样本数量、标签质量与置信区间；按业务漏报代价重新设门槛，评估阈值和拒答/转人工覆盖率；计入新增复核成本重新计算收益；保留原流程并缩小试点范围。必要时退回规则或简单 Workflow，复杂度不是交付价值。

**结课任务**：选择一个自己的业务场景，提交上述五份交付物。对每项结论注明“已测量”“教学假设”或“待验证”。对照 [毕业项目：完整示范与评分量规](/learn/ai-capstone) 自评，再请另一位读者按同一标准复核。理论选择题只测概念识别；系统设计和交付能力以可检查的项目产物验收。
