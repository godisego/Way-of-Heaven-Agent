# 造一个智能体

这篇是整个 Agent 径的**终章**——把前面 15 篇讲义里散落的零件装到一起，变成一个完整的智能体。

不学术，不用论文腔。我们就用"开一间茶馆"做类比，把造智能体的每一步讲清楚。

> **前置**：这篇假设你读完了 [AI Agent 全景图](/learn/ai-agent-panorama) 和 [LLM 基础原理](/learn/llm-fundamentals)。没读也能跟，但读了你才知道这一篇在干什么。

## 一 · 先搞清楚：智能体有哪些种类

不是所有智能体都长一样。先看全貌再决定你要造哪一种：

### 智能体的常见类型

| 类型 | 适合场景 | 典型代表 | 重心在哪 |
|------|---------|---------|---------|
| **通用智能体** | 什么都能干，泛场景多面手 | ChatGPT、Manus、Claude | 规划 + 工具链 + 广泛知识 |
| **编码智能体** | 软件开发：读写代码、跑测试、提 PR | Claude Code、Cursor、Devin | 代码理解 + 工具循环 + 长程任务 |
| **垂直/领域智能体** | 深耕某一领域，绑专属知识库 | 天道茶寮（命理）、客服、法务助手 | RAG 链路 + 知识库 + 校验 |
| **具身智能体** | 控制物理实体（机器人 / 车辆） | 人形机器人、自动驾驶 | 感知 + 决策 + 实时控制 |
| **科研智能体（AI4S）** | 驱动实验、数据分析、科学发现 | AlphaFold、材料筛选 | 数据管道 + 可复现 |

**天道茶寮属于「垂直/领域智能体」**——更准确说，是面向个人用户的命理垂直 agent。它不是 toB 的"企业"智能体，但技术栈相通：
- 绑定了命理 + 哲学的典籍库
- 有排盘工具（确定性计算，不是 LLM 生成）
- 有引用校验和声口校验
- 三贤分库检索 = 多角色协作雏形

### 你要造的可能是哪种？

- 想做一个"私人知识助手 / 某领域专家" → 垂直/领域智能体，重点在 RAG
- 想做一个"能自己上网搜信息干活的" → 通用智能体，重点在工具链
- 想做一个"帮写代码的" → 编码智能体，重点在代码理解 + 工具循环
- 想做一个"帮实验室跑数据分析的" → AI4S，重点在数据管道
- 想做一个"控制硬件 / 机器人的" → 具身智能体，重点在感知与控制

**下面以垂直/领域智能体为主线**讲全链路——因为天道茶寮就是这种，你可以在项目里直接对照看每一步怎么实现。

## 二 · 智能体的五大模块

一个完整的垂直/领域智能体包含五大模块：

```
├──────────┬──────────┬──────────┬──────────┬──────────┤
│ ① 需求拆解 │ ② 素材资源 │ ③ 工具能力 │ ④ 本体配置 │ ⑤ 调试优化 │
│          │          │          │          │          │
│ 用户是谁  │ 文档清洗  │ 插件/技能 │ 角色 prompt│ 意图识别率│
```

## 三 · 需求拆解——先想清楚再动手

> 类比：开茶馆前先想好"卖给谁、卖什么茶、什么必须做、什么绝对不做"

### 3.1 用户现在的基本情况

造智能体之前必须回答这些问题：

| 问题 | 天道茶寮的答案 | 你的答案 |
|------|--------------|---------|
| 用户是谁？ | 对命理/哲学感兴趣的普通人 | ______ |
| 用户的核心痛点？ | 想问命理但怕被骗，想深学但看不懂术语 | ______ |
| 用户的技术水平？ | 零基础，不会编程 | ______ |
| 用户愿意做什么？ | 填生辰、问问题、点引用看原文 | ______ |
| 用户不愿做什么？ | 付费、注册、看广告 | ______ |

**不搞清楚这五条就开干 = 茶馆开了但没人来。**

### 3.2 哪些是固定步骤（不交给 LLM 决定）

有些事必须确定性地做，不能让模型"自己决定"：

| 固定步骤 | 为什么不能交给 LLM | 天道怎么做的 |
|---------|-------------------|------------|
| 排盘（八字计算） | 模型会算错历法 | `baziCalculator.ts` 查表，模型完全不参与 |
| 真太阳时校正 | 模型不懂经度差 | `solarTime.ts` 数学计算 |
| 引用格式校验 | 模型会编引用 | `citationPolicy.ts` 程序校验 |
| 声口校验 | 模型会跑偏 | `voicePolicy.ts` 程序校验 |

**原则**：凡是"对就是对、错就是错"的事，用程序做；凡是"好不好、合不合适"的事，才交给模型。

### 3.3 哪些需要强制校验规则

强制校验 = 模型生成结果后，程序必须检查的硬性规则：

```
模型生成回答
    │
    ├→ [引用校验] 回答里的 [《书名》, 章节] 必须在检索结果里
    │   └→ 不在？→ 整组重写（只重试 1 次）
    │
    ├→ [声口校验] 老胡像老胡吗？玄像玄吗？李像李吗？
    │   └→ 不像？→ 整组重写
    │
    ├→ [资料不足检测] 检索结果是否为空？
    │   └→ 空？→ 直接返回"暂未入藏"，不调模型生成
    │
    └→ [内容安全] 是否有高风险内容（自杀/伤人等）？
        └→ 是？→ 触发安全兜底回应
```

→ 想深入：[引用校验设计](/learn/citation-design) · [验证计划](/learn/verification-plan)

## 四 · 素材资源准备——RAG 的地基

> 类比：茶馆的茶叶库——选什么茶、怎么存、怎么快速找到客人要的那一泡

这是整个智能体最重的部分。分四步：清洗 → 分块 → 向量化 → 入库。

### 4.1 文档清洗——垃圾进垃圾出

**清洗 = 把原始文档变成干净的、可检索的文本。**

常见清洗操作：

| 操作 | 什么时候需要 | 天道茶寮怎么做 |
|------|------------|-------------|
| 去除广告/页眉页脚 | 爬取的网页、扫描 PDF | 人工预处理后存为 .md |
| 统一编码 UTF-8 | 从不同来源收集的文档 | 上传时自动检测 |
| 去除空行/多余空格 | 任何文档 | `chunkPages.ts` 处理 |
| 标题提取 | Markdown 文档 | 按标题切分，标题作为 sectionTitle |
| 表格转文本 | PDF 里的表格 | 当前版本暂不支持表格 |
| OCR（图片转文字） | 扫描 PDF | 当前版本不支持，只取文本层 |

**关键原则**：清洗决定上限——清洗做得好，后面所有步骤都受益；清洗做不好，后面再调参也没用。

### 4.2 分块策略——切大切小的艺术

**分块（Chunking）= 把长文档切成小段，每段是一个检索单元。**

这是 RAG 里最影响效果的决策之一：

| 切大 | 切小 |
|------|------|
| 每段 1200~2000 字 | 每段 200~500 字 |
| 上下文完整，模型能理解整段意思 | 检索精准，命中后只带回相关部分 |
| 检索可能带回无关内容（一段里只有一句相关） | 可能丢失上下文（只看到半句话） |
| 适合叙事型文档（故事、论述） | 适合条目型文档（词典、FAQ） |

**天道茶寮的选择**：固定窗口 1200 字符 + 重叠 160 字符

```
原文：█████████████████████████████████████████████

切大（1200字 + 160字重叠）：
[████████████████████████]
          [████████████████████████]
                  [████████████████████████]

切小（300字）：
[████][████][████][████][████][████][████][████]
```

**为什么需要重叠**：如果不重叠，一句话刚好被切成两段——前半段在 chunk A 尾部，后半段在 chunk B 头部，两段都搜不全这句话。

**PDF 特殊处理**：不跨页切——每页是一个独立单元，引用时可以说"第 N 页"。

**Markdown 特殊处理**：不跨标题切——每个标题及其正文是一个单元，引用时说章节名。

→ 想深入：[RAG 代码走读](/learn/rag-walkthrough) · `src/core/ingestion/chunkPages.ts`

### 4.3 向量化——把文本变成数字

向量化（Embedding）= 把每段文字变成一串数字（向量），让计算机能算"语义相似度"。

```
"天干地支是八字的基础" → [0.043, -0.034, 0.044, ...]  （256 或 1536 维）
"甲乙丙丁是十天干"     → [0.041, -0.031, 0.045, ...]  （语义相近，向量也相近）
"量子力学"             → [0.12, 0.08, -0.03, ...]     （语义无关，向量差很远）
```

**两种模式**：

| 模式 | 原理 | 精度 | 需要 Key | 天道怎么配 |
|------|------|------|---------|-----------|
| Mock | SHA-512 hash + bigram | 低（字面匹配） | 不需要 | 默认，零配置可用 |
| Real | 调 Embedding API | 高（语义匹配） | 需要 | `OPENAI_COMPAT_*` 环境变量 |

→ 想深入：[向量检索实战](/learn/vector-search-hands-on)

### 4.4 入库——把向量存起来

入库 = 把 `文本 + 向量 + 来源信息` 写入向量库，供后续检索。

天道茶寮的每个 chunk 存这些字段：

```
{
  chunkId:    "chk_3ddb4b66...",    // 唯一 ID
  documentId: "doc_a2dd853d...",    // 所属文档
  sourceFileName: "存在主义笔记.md",  // 原始文件名
  bookTitle:  "存在主义笔记",        // 书名（用于引用显示）
  pageNumber: 1,                    // PDF 页码
  sectionTitle: "自由与选择",        // Markdown 标题
  tradition:  "existentialism",    // 分类（用于分库检索）
  text:       "自由意味着选择...",   // 原文
  embedding:  [0.043, -0.034, ...]  // 向量
}
```

**两种存储后端**：

| 后端 | 适合 | 天道怎么配 |
|------|------|-----------|
| Local JSON | 开发、学习、小规模 | `data/indexes/chunks.json`（默认） |
| Supabase pgvector | 生产、大规模、多用户 | `VECTOR_BACKEND=supabase` |

### 4.5 多库路由——三贤各查各的

天道茶寮的独特设计：**三个贤者各自有独立的典籍库**，检索时只查自己的：

```
用户提问："我怎么面对中年危机"
    │
    ├→ 老胡的库（yijing）
    │   └→ 命理判断边界与人事建议、周易六十四卦
    │
    ├→ 玄的库（daoism）
    │   └→ 道德经、庄子、列子
    │
    └→ 李的库（existentialism + stoicism）
        └→ 存在主义笔记、斯多葛可控圈
```

**为什么这样做**：
- 老胡不会用存在主义回答命理问题（口径不混）
- 每个角色的回答有独立证据基础
- 引用校验时可以精确判断"这个角色该不该引用这本书"

### 4.6 双路检索——关键词 + 语义

当前天道茶寮走单路检索（向量相似度）。完整的 RAG 系统通常用**双路检索**：

```
用户问题
    │
    ├→ [语义检索] embedding + 余弦相似度
    │   └→ 擅长：理解意图，"甲乙丙丁" 能匹配到 "天干"
    │
    ├→ [关键词检索] BM25 / TF-IDF
    │   └→ 擅长：精确匹配专有名词，"伤官见官" 能直接命中
    │
    └→ [融合排序] RRF（Reciprocal Rank Fusion）
        └→ 取两路各自的 topK，按排名倒数加权合并
```

| | 纯向量检索 | 纯关键词检索 | 双路融合 |
|---|---|---|---|
| "天干地支是什么" | ✅ 命中命理教材 | ✅ 直接匹配 | ✅✅ 双重确认 |
| "甲乙丙丁" | ✅ 语义匹配到天干 | ❌ 没有这四个字 | ✅ 至少一路命中 |
| "伤官见官" | ❌ 可能排到后面 | ✅ 精确匹配 | ✅ 关键词路兜底 |

**天道茶寮当前状态**：只有向量检索（mock 或 real），没有关键词路。如果你要加双路检索，可以在 `retrieveContext.ts` 里加一层 BM25 搜索，然后在 `searchChunksForMentors` 里做 RRF 融合。

## 五 · 工具能力——给智能体装手脚

> 类比：给茶馆掌柜配工具——账本（查资料）、电话（调外部服务）、计算器（跑数学）

### 5.1 插件 / 技能（Skill）封装

**工具（Tool/Skill）= 模型可以调用的确定性函数。**

天道茶寮的三个工具：

```
search_library(query: string)
  └→ 检索向量库，返回 topK 段落

read_source_unit(documentId: string, section: string)
  └→ 读某个文档的某个章节原文

ready_to_answer()
  └→ 告诉框架"证据够了，可以生成回答"
```

每个工具需要定义：

```typescript
{
  name: "search_library",          // 工具名（模型用这个名字调用）
  description: "检索典籍库",          // 告诉模型什么时候用这个工具
  parameters: {                     // JSON Schema 参数定义
    type: "object",
    properties: {
      query: { type: "string", description: "搜索关键词" }
    },
    required: ["query"]
  }
}
```

**关键原则**：
- 工具的 `description` 要写清楚——模型靠这段文字判断"该不该调这个工具"
- 参数要有 JSON Schema 校验——模型可能传错类型，框架要拦截
- 工具执行有超时——模型可能在循环里反复调同一个工具

→ 想深入：[工具循环设计](/learn/agent-loop) · `src/core/agent/toolRegistry.ts`

### 5.2 HTTP 接口——调外部服务

智能体经常需要调外部 API（天气、搜索、数据库等）。封装 HTTP 工具的要点：

```typescript
// 一个 HTTP 工具的基本结构
{
  name: "search_web",
  description: "搜索互联网获取最新信息",
  parameters: {
    type: "object",
    properties: {
      query: { type: "string" }
    },
    required: ["query"]
  },
  handler: async (params) => {
    const res = await fetch(`https://api.search.com?q=${params.query}`);
    const data = await res.json();
    // 截断——工具返回内容不能太长，否则撑爆上下文窗口
    return { text: data.summary.slice(0, 800) };
  }
}
```

**三个必须注意的点**：
1. **超时**：HTTP 请求必须设超时（天道茶寮用 10s）
2. **截断**：返回内容不能超过上下文窗口的 1/4
3. **错误处理**：API 报错时要返回结构化错误，让模型知道该换个方法

### 5.3 代码节点——跑确定性逻辑

有些逻辑不适合用 LLM 做（不精确、不稳定），用代码更合适：

| 场景 | 为什么不用 LLM | 天道怎么做的 |
|------|-------------|------------|
| 八字排盘 | 历法计算必须 100% 精确 | `baziCalculator.ts` 代码实现 |
| 真太阳时校正 | 涉及经度/均时差数学 | `solarTime.ts` 代码实现 |
| 五行统计 | 数数不能数错 | `explainChart.ts` 代码实现 |
| 十神计算 | 干支关系是确定的 | `mingliKb.ts` 代码实现 |

**原则**：如果一个操作有"标准答案"，就用代码做，不要让模型猜。

### 5.4 工作流编排——工具怎么串起来

工作流 = 多个工具按特定顺序/条件组合：

```
天道茶寮的默认工作流（Agent 循环）：

步骤1: 模型分析问题 → 决定要不要检索
步骤2: 模型调 search_library → 框架执行 → 返回结果
步骤3: 模型看结果够不够 → 不够？调 read_source_unit 读原文
步骤4: 模型判断证据够了 → 调 ready_to_answer
步骤5: 框架把所有证据拼成 context → 生成三贤回答
步骤6: 引用校验 + 声口校验 → 不通过？重写一次
```

**两种工作流模式**：

| 模式 | 特点 | 天道怎么切的 |
|------|------|------------|
| **Agent 模式**（默认） | 模型自己决定调什么工具、调几次 | 对谈界面不开"循迹"开关 |
| **RAG 模式**（循迹） | 固定流程：检索一次→生成一次 | 对谈界面开"循迹"开关 |

Agent 模式更灵活但更慢更贵；RAG 模式更快更省但只能查一次。**两种模式都有用——天道茶寮都保留了。**

→ 想深入：[工具循环设计](/learn/agent-loop)

## 六 · 本体配置——智能体的"灵魂"

> 类比：茶馆掌柜的人设——他是什么人、会什么、不会什么、说话什么风格

### 6.1 角色 prompt

角色 prompt = 系统提示词，定义"你是谁"。天道茶寮三贤的 prompt 结构：

```
[身份]
你是老胡，一位盲派算师，在茶寮常驻。

[能力边界]
- 能做：基于检索到的命理典籍给实战建议
- 不能做：恐吓式断语、直断吉凶、编造出处

[风格]
说话直给、不绕弯、用大白话。

[引用格式]
必须使用 [《书名》, 章节] 格式引用出处。

[兜底规则]
如果典籍里没有相关内容，明说"暂未入藏"，不编造。
```

**五个必填字段**：身份、能力边界、风格、引用格式、兜底规则。缺任何一个，模型都可能跑偏。

→ 想深入：[Prompt Engineering 入门](/learn/prompt-engineering) · `src/data/mentors.ts`

### 6.2 边界约束

边界约束 = "绝对不能做什么"：

| 约束类型 | 例子 | 怎么实现 |
|---------|------|---------|
| 内容红线 | 不预测生死、不直断吉凶 | prompt 里写 + 程序检测 |
| 格式约束 | 必须用三贤格式 | `wrapAsMentorDialogue` 程序包装 |
| 引用约束 | 只能引用检索到的段落 | `citationPolicy` 程序校验 |
| 声口约束 | 老胡不能像学者写论文 | `voicePolicy` 程序校验 |
| 安全约束 | 高风险内容触发兜底 | `rateLimit` + 安全提示 |

### 6.3 绑定知识库

每个角色绑定哪些典籍库（tradition）：

| 角色 | 绑定库 | 为什么 |
|------|-------|--------|
| 老胡 | yijing（命理+易传） | 命理实战需要命理典籍 |
| 玄 | daoism（道家） | 玄谈气机需要道家经典 |
| 李 | existentialism + stoicism | 存在主义导师需要哲学典籍 |

绑定 = 检索时只搜这些 tradition 的 chunk。代码在 `retrieveContext.ts` 的 `isSourceAllowedFor` 函数。

### 6.4 规划模式设定

规划模式 = Agent 怎么决定下一步做什么：

| 模式 | 描述 | 适合 | 天道用的 |
|------|------|------|---------|
| **无规划** | 每步临时决定 | 简单任务 | ✅ 当前版本 |
| **预设计划** | 先生成计划再执行 | 复杂多步任务 | 蓝图里有，未实现 |
| **动态重规划** | 每步根据结果调整计划 | 高级 Agent | 未来目标 |

天道茶寮当前是"无规划"——模型每步临时决定调什么工具。这对于"问一个问题"够了，但对于"帮我写一份报告"这种复杂任务不够。

## 七 · 调试与优化——让智能体从"能用"变"好用"

> 类比：茶馆开了几天后——客人说茶太淡、等太久、掌柜话太多。要调。

### 7.1 五个核心指标

| 指标 | 怎么测 | 天道怎么做的 |
|------|--------|------------|
| **意图识别成功率** | 问 100 个问题，模型选对工具的比例 | 看 `trace` 里第一步选了什么工具 |
| **工具调用正确率** | 模型传的参数是否合法 | 看 `trace` 里参数是否通过 schema 校验 |
| **召回质量** | 检索 topK 里有没有相关内容 | `/api/search` 看返回的 score 和内容 |
| **幻觉率** | 回答里有没有编造的内容/引用 | 引用校验拦截率 + 人工抽检 |
| **异常兜底率** | 出错时是否稳定停止 | 看是否返回"暂未入藏"而非崩溃 |

### 7.2 调什么、怎么调

```
回答不好
    │
    ├→ 引用错误（编了引用）
    │   └→ 检查 citationPolicy 是否拦住
    │       └→ 拦住了？→ prompt 加约束
    │       └→ 没拦住？→ 校验逻辑有 bug，修
    │
    ├→ 回答跑题
    │   ├→ 检索没命中 → 调 chunking 或换 embedding 模型
    │   └→ 检索命中但模型没用 → 调 prompt（强调"必须基于检索结果回答"）
    │
    ├→ 角色跑偏（老胡像学者）
    │   └→ 声口校验没拦住 → 加 voicePolicy 规则
    │
    ├→ 回答太长/太短
    │   └→ prompt 加长度约束
    │
    └→ 回答空洞（套话连篇）
        └→ prompt 加反空洞规则 + 最低信息密度要求
```

### 7.3 调切片（Chunking）

如果检索质量差，先看切片：

| 症状 | 可能原因 | 怎么调 |
|------|---------|--------|
| 搜"天干"返回无关内容 | chunk 太大，一段里什么都有 | 缩小 chunk size |
| 搜"伤官见官"找不到 | chunk 太小，上下文丢了 | 加大 chunk size 或重叠 |
| 命理内容排哲学后面 | mock embedding 不懂语义 | 换 real embedding |
| 换了模型后搜索报错 | 维度变了 | `npm run reindex:embeddings` |

### 7.4 调 Rerank

Rerank = 检索后用更精准的模型重新排序。当前天道茶寮没有 rerank，但加法很简单：

```typescript
// 在 retrieveContext.ts 里加一层
const candidates = await vectorStore.search(queryEmbedding, topK * 3);  // 多取 3 倍
const reranked = await rerankModel.rerank(query, candidates, topK);    // 精排 topK
```

Rerank 模型（如 bge-reranker、cohere-rerank）比 embedding 更贵但更准——适合对精度要求高的场景。

### 7.5 调 Prompt

| 症状 | 怎么调 prompt |
|------|-------------|
| 模型不引用 | 加"必须引用检索结果的至少一处" |
| 模型编引用 | 加"只能引用 Sources 列表里给出的 cite_as" |
| 模型回答太学术 | 加"用大白话，不要用学术术语" |
| 模型回答太长 | 加"不超过 200 字" |
| 模型套话 | 加"不要用'让我们一起来探讨'之类的话术" |

### 7.6 边界 Case 测试

必须测的边界情况：

| Case | 预期行为 | 天道怎么测 |
|------|---------|-----------|
| 空问题 | 返回"问题不能为空" | API 路由校验 |
| 库里没有的内容 | 返回"暂未入藏" | `noEvidenceAnswer` |
| 高风险内容 | 安全兜底 | `rateLimit` |
| 模型不按格式输出 | `wrapAsMentorDialogue` 包装 | `noEvidenceAnswer` |
| 引用全错 | 清空引用 + 警告 | `citationPolicy` |
| 工具调用超时 | 稳定停止 | `orchestrator` |
| 步数耗尽 | 稳定停止 | `orchestrator` |

→ 想深入：[系统化验证计划](/learn/verification-plan) · [M5 验收](/learn/m5-acceptance)

## 九 · 完整链路图

把上面所有步骤连起来——这就是一个智能体从 0 到 1 的完整链路：

```
需求拆解          素材资源              工具能力           本体配置           调试优化
  │                │                    │                 │                 │
  ├ 用户画像       ├ 文档清洗            ├ 插件/技能定义     ├ 角色 prompt     ├ 意图识别率
  ├ 固定步骤       ├ 分块策略            ├ HTTP 接口封装    ├ 边界约束       ├ 工具调用率
  ├ 强制校验规则    ├ 向量化              ├ 代码节点         ├ 绑定知识库     ├ 召回质量
  │               ├ 入库                ├ 工作流编排       ├ 规划模式       ├ 幻觉率
  │               ├ 多库路由            │                 │                 ├ 异常兜底
  │               └ 双路检索            │                 │                 └ 边界 Case
  │                 │                    │                 │                 │
  ▼                 ▼                    ▼                 ▼                 ▼
  ┌─────────────────────────────────────────────────────────────────────────────┐
  │                              交付与标准化                                     │
  │  Demo 打包 → 培训材料 → 标准化素材 → 版本管理                                  │
  └─────────────────────────────────────────────────────────────────────────────┘
```
