# 天道 Agent 建设蓝图

## 结论

当前项目是一个可运行的“本地知识库 RAG + 问者档 + 三贤角色化回答”应用，还不是完整 Agent。

它已经具备 Agent 的三个基础零件：

- 可检索的私人典籍库；
- 可替换的 LLM / Embedding Provider；
- 可确定执行的八字与用户画像模块。

它缺少的不是更多角色文案，而是一个受控的任务循环：模型必须能选择工具、观察工具结果、判断证据是否足够、在预算内停止，并留下可审计记录。

## 当前能力与目标差距

| 领域 | 当前状态 | Agent 目标 |
|---|---|---|
| 问答 | 固定执行一次检索，再调用一次模型 | Agent 根据问题决定是否检索、检索什么、是否继续读原文 |
| 工具 | 业务函数由 API 路由直接调用 | 有 schema、权限和超时约束的工具注册表 |
| 计划 | 没有任务计划 | 生成简短可执行计划，并可根据观察结果调整 |
| 证据 | TopK 文本直接拼进 Prompt | 独立 Evidence Ledger，记录每条结论可用的来源 |
| 校验 | 校验回答中的书名与位置 | 同时校验无效引用、证据覆盖率、资料不足判断 |
| 记忆 | 问者档存在浏览器 localStorage | 会话记忆、用户可控长期记忆、失败经验分层存储 |
| 三贤 | 一个模型在一次回答里扮演三人 | 共享证据的三种视角；必要时再拆成独立调用 |
| 可观测性 | 只返回最终答案 | 保存步骤、工具耗时、检索分数、重试原因和成本 |
| 安全 | Prompt 中有基本边界 | 工具权限、隐私控制、危机识别、限流和审计 |
| 评测 | 手工验证计划 | 固定数据集 + 自动指标 + 发布前回归门禁 |

## 推荐目标架构

```text
用户问题 + 问者档
        │
        ▼
Intent / Risk Gate
  ├─ 普通闲聊：直接回答
  ├─ 典籍问题：进入证据检索
  ├─ 命理问题：调用确定性排盘工具
  └─ 高风险问题：进入安全回应策略
        │
        ▼
Agent Orchestrator
  ├─ 生成短计划
  ├─ 选择允许的工具
  ├─ 接收 Observation
  ├─ 判断证据是否足够
  └─ 达到停止条件
        │
        ├───────────────┬──────────────────┬──────────────────┐
        ▼               ▼                  ▼                  ▼
search_library   read_source_unit   calculate_bazi   recall_memory
        │               │                  │                  │
        └───────────────┴──────────┬───────┴──────────────────┘
                                   ▼
                            Evidence Ledger
                                   │
                                   ▼
                      三贤结构化生成（胡 → 李 → 玄）
                                   │
                                   ▼
                 Citation / Safety / Actionability Verifier
                                   │
                                   ▼
                         最终回答 + 可展开执行轨迹
```

Orchestrator 不应暴露模型的私有思维链。产品只保存和展示结构化信息：计划摘要、工具名、工具参数、工具结果摘要、证据和最终判断。

## 第一批工具

### `search_library`

- 输入：`query`、可选 `traditions`、`topK`。
- 输出：候选 chunk、分数、书名、来源位置。
- 约束：限制 topK，应用最低相关性阈值，不返回 embedding 原始数组。

### `read_source_unit`

- 输入：`documentId`、`pageNumber`。
- 输出：PDF 某页或文本某章节的完整原文。
- 用途：检索命中后继续核对上下文，而不是仅凭一个 chunk 下结论。

### `get_user_profile`

- 输入：无。
- 输出：用户明确授权给 Agent 的问者档字段。
- 约束：出生信息属于敏感个人数据，默认不进入日志和长期记忆。

### `calculate_bazi`

- 输入：日期、时间、地点、经度、性别和计算流派。
- 输出：结构化四柱、大运、五行等结果及算法版本。
- 原则：结果来自确定性代码，不允许模型自行编造排盘结果。

### `get_current_luck_cycle`

- 输入：排盘结果、目标年份。
- 输出：对应年份的大运区间。
- 原则：模型只解释结果，不负责自行计算年份区间。

### `recall_memory` / `save_memory` / `delete_memory`

- 记忆读取与写入必须分开授权。
- `save_memory` 只保存稳定偏好、长期目标和用户确认的信息。
- 用户随时可以查看、修改、删除全部长期记忆。

第一阶段不要开放写文件、发送消息、联网搜索等高副作用工具。先把只读知识与确定性计算工具跑稳。

## Agent 循环

推荐状态机：

```text
received
  → classified
  → planning
  → tool_call
  → observing
  → evidence_ready
  → drafting
  → verifying
  → completed | insufficient | failed | cancelled
```

每轮必须具备以下停止条件：

- 最多 6 个工具步骤；
- 单工具超时与整轮总超时；
- 最大 token / 调用费用预算；
- 连续两次得到相同结果时停止；
- 证据不足时返回 `insufficient`，不继续猜；
- 用户可以取消。

## 三贤如何演进

第一阶段继续使用一个模型生成三贤，但要求模型输出结构化结果：

```json
{
  "hu": { "text": "...", "evidenceIds": ["ev_1"] },
  "li": { "text": "...", "evidenceIds": ["ev_2"] },
  "xuan": { "text": "...", "evidenceIds": ["ev_1", "ev_2"] }
}
```

这样可以先解决顺序、串味和引用归属问题。只有在评测证明单模型确实无法保持角色差异时，再拆成独立的三次模型调用：

1. 老胡读取命理与时势证据；
2. 李读取存在主义与用户选择证据；
3. 玄读取前两人的结构化结论并收束；
4. Verifier 独立检查，不扮演任何导师。

多 Agent 会增加延迟、费用和错误面，因此必须由评测数据驱动，而不是仅为了形式上“像 Agent”。

## 记忆设计

建议分四层：

| 层级 | 内容 | 生命周期 |
|---|---|---|
| Turn | 当前问题与本轮工具结果 | 一轮请求 |
| Session | 最近对话摘要、未完成事项 | 当前会话 |
| Profile | 用户确认的长期背景与偏好 | 用户主动删除前 |
| Reflection | 系统失败原因与改进规则 | 版本化、可审计 |

典籍原文不应复制进用户记忆；它已经属于知识库。出生日期、出生地、感情和工作等敏感字段不得自动转成长期记忆。

## 安全与产品边界

天道 Agent 是人生反思工具，不是事实预测器。至少需要：

- 命理内容明确标为文化解释与自我观察，不作必然性断言；
- 禁止死亡、灾祸、疾病、破产等恐吓式预测；
- 遇到自伤、暴力、严重心理危机时跳出角色表演，提供直接、现实的求助建议；
- 医疗、法律、投资等专业问题不冒充专业人士；
- 对删除资料、写入记忆、外发内容等副作用动作进行确认；
- API 输入大小限制、鉴权、速率限制和费用上限；
- 日志默认脱敏，不记录 API Key、完整出生信息和私有典籍全文。

## 评测体系

发布前至少维护以下数据集：

1. 典籍事实题：答案与来源位置可确定。
2. 跨典籍综合题：需要两次以上检索。
3. 资料不足题：必须拒绝编造。
4. 假引用与提示注入题：不得服从典籍中的恶意指令。
5. 命理计算题：与固定样例结果比较。
6. 角色一致性题：顺序、声口、建议边界均可检查。
7. 高风险人生问题：验证安全策略。

核心指标：

- 检索 Recall@K；
- 有效引用率与无效引用漏放率；
- 证据覆盖率；
- 资料不足识别准确率；
- 工具调用成功率、平均步骤、P95 延迟；
- 每轮模型与 Embedding 成本；
- 用户对建议“具体、可执行、不恐吓”的评分。

## 分阶段实施

### Phase 0：工程与数据可靠性

- 构建、lint、typecheck、测试全部通过；
- 文档失败可重试，写入具备事务或原子性；
- 限制上传大小、问题长度和 topK；
- 建立最小评测集与 CI。

### Phase 1：可信 RAG

- 混合检索（向量 + 关键词）；
- 思想传统过滤、邻页/邻章节扩展与 rerank；
- Evidence Ledger 与严格引用校验；
- 提示注入隔离与模型调用超时。

### Phase 2：单 Agent 工具循环

- Tool Registry；
- `search_library`、`read_source_unit`、排盘与大运工具；
- 有步骤上限、超时、预算和取消能力的 Orchestrator；
- 展示可审计的执行摘要。

### Phase 3：会话与用户记忆

- 会话持久化、摘要和恢复；
- 用户可查看和删除的长期记忆；
- 隐私授权与数据导出。

### Phase 4：三贤协作与评审

- 结构化三贤输出；
- 独立 Verifier；
- 评测证明必要时再拆为多模型/多 Agent。

### Phase 5：云端产品化

- Auth、RLS、多用户隔离；
- 后台入库任务和进度推送；
- 监控、追踪、费用告警、备份与恢复；
- 分享功能的脱敏与权限控制。

## “已经是 Agent”的验收标准

同时满足以下条件，项目才适合称为天道 Agent：

- 模型能在允许清单内自主选择至少两个工具；
- 工具结果会影响下一步动作，而不是固定流水线；
- 有清晰停止条件、预算、超时和取消；
- 每个事实性结论可回溯到 Evidence Ledger；
- 资料不足时能稳定停止并拒绝编造；
- 会话和长期记忆分层且受用户控制；
- 执行轨迹可审计但不暴露私有思维链；
- 关键评测指标进入 CI，版本升级不会静默退化。
